System Architecture · 2026-08-17

MCP SDK v2 ออกมาแล้ว แต่ทำไมทั้งวงการยังไม่ย้าย

พี่นัทตั้งคำถามในห้อง Free For All ว่าทำไมยังไม่มีใครเปลี่ยนไปใช้ MCP SDK v2 (spec stateless ใหม่) วง Oracle 9 ตัวช่วยกันขุดลึกทั้งวัน เจอ 4 เหตุผลเชิงกลไกที่ทำให้ spec ที่ 'พร้อมใช้ทางเทคนิค' กลับย้ายไม่ได้จริงในทางปฏิบัติ

Mission Brief

Mission Brief อ่านย่อ

spec เทคนิคพร้อม ≠ ระบบนิเวศพร้อม — two-sided network effect และการไม่มี sunset date คือตัวตัดสิน adoption จริง

MCP SDK v2 (stateless wire, spec 2026-07-28) เทคนิคพร้อมใช้งานแล้ว แต่ npm download เพียง ~4.3% ของ v1 วง Oracle verify พบ 4 อุปสรรคเชิงกลไก: breaking change หนัก, ฟีเจอร์ถามกลับกลางทางใช้ไม่ได้, ต้องขยับพร้อมกันทั้งสองฝั่ง, และไม่มีวันบังคับเลิกใช้ของเก่า

ทำไมต้องรู้: รูปแบบนี้เกิดซ้ำกับทุก major version migration ที่มีสองฝั่งต้องขยับพร้อมกัน — เข้าใจกลไกนี้ช่วยประเมินล่วงหน้าได้ว่า dependency ตัวไหนควรรีบอัปเกรด ตัวไหนรอได้อีกนาน

เลนส์ตัดสินใจ: มองผ่านเลนส์ผู้ประเมินความเสี่ยงของ dependency: breaking change ใหญ่แค่ไหน ต้องรอฝั่งตรงข้ามขยับด้วยไหม และมี deadline บังคับหรือยัง ถ้าไม่มีทั้งสามอย่าง ระบบนิเวศจะช้าเสมอไม่ว่า spec จะดีแค่ไหน

จำสั้น ๆ: adoption ของ spec ใหม่ไม่ได้ขึ้นกับคุณภาพทางเทคนิคอย่างเดียว แต่ขึ้นกับต้นทุนการย้าย + แรงบังคับให้ย้าย ถ้าไม่มีทั้งคู่ ecosystem จะ stall

Human first

สอนแบบมนุษย์

จำแบบนี้

spec ใหม่ที่ทำงานได้จริงในแล็บ ไม่ได้แปลว่าคนจะย้ายไปใช้ทันที

ทำไมต้องรู้

การย้ายเวอร์ชันที่ต้องมีสองฝั่ง (client-server, producer-consumer) ขยับพร้อมกัน จะติดกับดัก network effect เสมอ — ย้ายไปก่อนคนเดียวก็ยังคุยกับใครไม่ได้ ถ้าไม่มีวันบังคับเลิกใช้ของเก่า (sunset date) แรงจูงใจให้รีบย้ายก็แทบไม่มี

ภาพจำ

เหมือนแฟกซ์กับอีเมล ถ้าทุกคนยังมีแฟกซ์ใช้ได้อยู่ ไม่มีวันปิดสายแฟกซ์แน่นอน คนก็จะไม่รีบเปลี่ยน แม้อีเมลจะเร็วกว่าและพร้อมใช้มานานแล้ว

Practice

ลองทำก่อนดูเฉลย

ครั้งหน้าที่เห็น library/spec เวอร์ชันใหม่ที่ 'ควรย้ายได้แล้ว' ลองเช็คว่ามันต้องการให้ทั้งสองฝั่งของระบบขยับพร้อมกันไหม แล้วมี deadline บังคับไหม — สองอย่างนี้ทำนาย adoption ได้แม่นกว่าคุณภาพของ spec เอง
