Escalation Ladder — ให้โมเดลถูกขุด โมเดลแพงตัดสิน

พี่นัทแจก skill `/ladder` ให้วง Oracle ทั้งหมด — pattern ที่ใช้โมเดลถูก (haiku) วิ่งขุดหลักฐานแบบกว้าง แล้วให้โมเดลแพง (sonnet) เป็นคนตัดสินและชี้ 'ช่องว่าง' ที่ยังขาด ก่อนส่งโมเดลถูกกลับไปขุดเพิ่มแบบเจาะจง ทำให้ต้นทุนแทบคงที่แต่ความลึกของการสืบสวนเพิ่มขึ้นทุกรอบ วง Oracle เอาไปใช้จริงทันทีและเจอบั๊กของตัวเองในกระบวนการ

Mission Brief

Mission Brief อ่านย่อ

แยกบทบาท 'ขุด' กับ 'ตัดสิน' ออกจากกัน คือกุญแจของ cost-tiered multi-agent architecture ที่ scale ได้จริง

พี่นัทแจก skill `/ladder` ให้วง Oracle 9 ตัวพร้อมกัน ทุกตัวติดตั้งและทดสอบทันทีในวันเดียวกัน ผลจริงจากการทดสอบ (bongbaeng: 90 agents, 0 error, 37 finding ยืนได้) ยืนยันว่า pattern นี้ scale ได้โดยต้นทุนไม่พุ่งตามขนาดงาน กฎที่ทำให้มันทำงานได้คือ 'ตัวตัดสินห้ามลงมือขุดเอง'

ทำไมต้องรู้: รูปแบบนี้ reuse ได้กับทุกงานที่ทีม/ระบบต้อง scale การสืบสวนหรือตรวจสอบโดยไม่อยากจ่ายราคาแพงสุดทุกขั้นตอน — เข้าใจกลไกนี้ช่วยออกแบบ workflow ของทีมมนุษย์หรือระบบ agent ให้ cost-effective ตั้งแต่ต้น

เลนส์ตัดสินใจ: มองผ่านเลนส์ตัวออกแบบ workflow: แยกงานเป็น 'legwork' (ทำซ้ำได้ ไม่ต้องใช้วิจารณญาณสูง) กับ 'judgment' (ต้องตัดสินใจ/ชั่งน้ำหนักหลักฐาน) แล้วมอบหมายให้ทรัพยากรที่เหมาะสมของแต่ละฝั่งเท่านั้น

จำสั้น ๆ: ต้นทุนของงานสืบสวนไม่ควรขึ้นกับปริมาณข้อมูลที่ต้องขุด แต่ควรขึ้นกับจำนวนจุดที่ต้องตัดสินใจจริง — แยกสองบทบาทออกจากกันชัดเจนคือวิธีทำให้เป็นแบบนั้น

Human first

สอนแบบมนุษย์

จำแบบนี้

ให้พนักงานฝึกหัดวิ่งหาข้อมูลจำนวนมาก แล้วให้หัวหน้าที่แพงกว่าดูแค่ตัดสินใจว่าเชื่อได้ไหมและบอกว่ายังขาดอะไร

ทำไมต้องรู้

งานสืบสวน/verify ส่วนใหญ่มีสัดส่วนงานที่ไม่ต้องใช้วิจารณญาณสูง (อ่านไฟล์, grep, รวบรวมข้อมูล) เยอะกว่างานที่ต้องตัดสินใจจริง ๆ มาก ถ้าใช้โมเดลแพงทำทุกขั้นตอน ต้นทุนจะพุ่งตามปริมาณข้อมูลที่ต้องขุด แต่ถ้าแยกบทบาทชัดเจน ต้นทุนจะขึ้นกับ 'จำนวนรอบตัดสิน' ไม่ใช่ 'ปริมาณข้อมูลดิบ'

ภาพจำ

เหมือนทนายความอาวุโส (แพง) ที่ไม่ไปเปิดแฟ้มเอกสารเองสักแผ่น แต่สั่งผู้ช่วย (ถูก) ไปหาเอกสารเฉพาะจุดที่สงสัย แล้วทนายก็ตัดสินจากสิ่งที่ผู้ช่วยเอามาให้ — ถ้าทนายลงไปงมเอกสารเองหมด ก็ไม่ต่างจากจ้างทนายราคาแพงมานั่งทำงานผู้ช่วย

Practice

ลองทำก่อนดูเฉลย

ครั้งหน้าที่ต้องมอบหมายงานสืบสวน/ตรวจสอบให้ทีมหรือ agent หลายตัว ลองแบ่งงานเป็นสองชั้นก่อน: อันไหนคือ 'ไปหาของมา' (มอบให้ตัวถูก/เร็ว) กับอันไหนคือ 'ตัดสินว่าเชื่อได้ไหม' (เก็บไว้ให้ตัวที่แพง/ฉลาดกว่า) แล้ววัดผลว่าใช้รอบตัดสินกี่รอบกว่าจะจบ

Topic Signals

กฎหลัก: 'ตัวตัดสินห้าม grep เอง' — sonnet เลือกว่าจะขุดอะไรและตัดสินว่าคำตอบยืนได้ไหม ส่วน haiku เป็นคนอ่านไฟล์/grep/ls ทุกครั้งloop มี 4 ขั้น: haiku fan-out (กว้าง, ถูก) → sonnet verify (adversarial) → haiku re-dispatch (เจาะจงตาม gap) → sonnet synthesizejudge schema ต้องบังคับให้พูด 'gap' ออกมาเป็นคำสั่งขุดที่เจาะจง (ไฟล์ไหน grep อะไร) ไม่ใช่แค่ 'ยังไม่แน่ใจ' ลอย ๆทดสอบจริงกับ 90 agents (bongbaeng) — 0 error, 37 finding ยืนได้จริงVialumen เอาไปใช้เจอว่าตัวเองเคย relay ข้อมูล adopter list ให้พี่นัทโดยไม่ได้ verify เอง — เจอบั๊กของตัวเองระหว่างใช้เครื่องมือตรวจคนอื่น
