Section 1

1 · ตัวโมเดล

เริ่มจากของจริงที่อยู่ล่างสุด: โมเดลคืออะไร ทำอะไรได้จริง และค่าใช้จ่ายเกิดตรงไหน

AI

ปัญญาประดิษฐ์ — ป้ายชื่อที่ขยับไปเรื่อย ๆ ไม่ใช่เทคโนโลยีตัวใดตัวหนึ่ง ตอนนี้ชี้ไปที่ large language model

ทำไมต้องรู้
เวลาใครพูดว่า AI ให้ถามต่อว่าหมายถึงโมเดลตัวไหน เพราะคำนี้เปลี่ยนความหมายทุก 2-3 ปี
อ่านเต็ม

ป้ายชื่อที่ขยับความหมายไปเรื่อย ๆ ตามยุค ไม่ใช่เทคโนโลยีตัวเดียวที่นิ่ง ทศวรรษ 1950 หมายถึงการพิสูจน์ทฤษฎีบทด้วยกฎ, 1980 หมายถึง expert system ที่เขียนกฎมือเป็นพัน, 1990 หมายถึงการค้นต้นไม้เกม (Deep Blue ชนะ Kasparov), 2010 หมายถึง deep learning, ตอนนี้หมายถึง large language model กลไกที่ทำให้คำนี้ขยับเรียกว่า AI effect: พอเทคนิคไหนใช้ได้จริงแน่นอนแล้ว คนจะเปลี่ยนไปเรียกชื่อเฉพาะแทน ("แค่ search", "แค่สถิติ") แล้วคำว่า AI ก็เลื่อนไปจับสิ่งที่ยังแก้ไม่ได้ต่อไป เวลาคุยกันเรื่อง AI แล้วหลงประเด็น มักเพราะแต่ละคนพูดถึงคนละยุคโดยไม่รู้ตัว ทางแก้คือเปลี่ยนคำว่า AI เป็นคำเฉพาะที่หมายถึงจริง เช่น โมเดลตัวไหน harness แบบไหน หรือ context ที่ให้ไป

Model

โมเดล — ก้อนตัวเลขที่ทำได้อย่างเดียวคือทายคำถัดไป ไม่มีความจำ ไม่ทำอะไรเองได้

ทำไมต้องรู้
คนมักโทษ 'โมเดลโง่' ทั้งที่ปัญหาส่วนใหญ่อยู่ที่ harness และ context รอบตัวมัน
อ่านเต็ม

คือก้อนพารามิเตอร์ล้วน ๆ ไม่มีอะไรมากกว่านั้น ทำได้อย่างเดียวคือทายโทเคนถัดไป ไม่มีสถานะค้างจากก่อนหน้า อ่านไฟล์เองไม่ได้ รันคำสั่งเองไม่ได้ จำเมื่อวานไม่ได้ — ทุกอย่างที่ดูเหมือน agent กำลังทำงาน (เลือก tool, อ่านผล, วนจนกว่าจะเสร็จ) คือ harness เอาผลทายคำของโมเดลมาต่อกันเป็นลูปต่างหาก ผู้ให้บริการมักมีโมเดลหลายขนาดให้เลือก: ตัวใหญ่ฉลาดแต่ช้าแพง ตัวเล็กเร็วถูกแต่โง่กว่า เลือกให้เหมาะงาน — ตัวใหญ่ไว้วางแผน/ดีบักยาก ตัวเล็กไว้แก้ไขจักรกล พอพูดว่า "โมเดลมันแย่เรื่องนี้" ให้เช็คก่อนว่าปัญหาจริง ๆ อยู่ที่ context หรือ harness หรือเปล่า ผลงานที่น่าผิดหวังส่วนใหญ่ไม่ได้มาจากพารามิเตอร์

Parameters

พารามิเตอร์ / weights — ตัวเลขหลักพันล้านข้างในโมเดล ปรับตอนเทรน ทุกอย่างที่โมเดลรู้อยู่ในนี้

ทำไมต้องรู้
อธิบายว่าทำไมโมเดลถึงรู้บางเรื่องโดยไม่ต้องบอก และทำไมสอนเพิ่มระหว่างใช้งานไม่ได้
อ่านเต็ม

ตัวเลขนับพันล้านตัวข้างในโมเดล ปรับค่าตอนเทรน ทุกอย่างที่โมเดล "รู้" อยู่ในตัวเลขพวกนี้ ไม่มีฐานข้อมูลข้อเท็จจริงหรือตารางค้นหาอยู่ข้างในเลย มีแต่ตัวเลขที่จัดเรียงจนการคำนวณให้ผลลัพธ์ที่มีประโยชน์ จุดสำคัญคือพารามิเตอร์แช่แข็งหลังเทรนเสร็จ ไม่มีอะไรที่ทำใน session เปลี่ยนมันได้เลย — ไม่มีการแก้ไขไหน ไม่มีโค้ดที่โชว์ให้ดู ไม่มีความผิดพลาดไหนที่มันเรียนรู้ได้ ทุก session รันบนตัวเลขชุดเดียวกัน วิธีเดียวที่จะเปลี่ยนพารามิเตอร์คือเทรนใหม่ ซึ่งจะได้โมเดลอีกตัวไปเลย ถ้าอยากให้มันรู้จักโค้ดเบสหรือ SDK ภายในของเรา ทางที่คุ้มกว่าคือยัดเข้า context ไม่ใช่ fine-tune

Training

การเทรน — กระบวนการป้อนข้อความมหาศาลเพื่อปรับพารามิเตอร์ให้ทายคำถัดไปแม่นขึ้น

ทำไมต้องรู้
จบเมื่อไหร่ ความรู้ก็แช่แข็งเมื่อนั้น ต่อจากนั้นต้องป้อนผ่าน context อย่างเดียว
อ่านเต็ม

กระบวนการปรับพารามิเตอร์ของโมเดล โดยป้อนข้อความมหาศาลแล้วปรับตัวเลขให้ทายคำถัดไปแม่นขึ้นเรื่อย ๆ เป็นการทำครั้งเดียวก่อนปล่อยโมเดล มีสองช่วง: pre-training (รันหลักก้อนใหญ่) กับ post-training (ปรับละเอียด เช่นสอนให้ทำตามคำสั่ง สอนเรื่องความปลอดภัย) แต่ระดับนี้ไม่ต้องแยกก็ได้ กลไกคือทำซ้ำระดับมหาศาล: ให้ดูข้อความ ให้ทายคำถัดไป ปรับพารามิเตอร์ให้เข้าใกล้คำจริง ทำซ้ำนับล้านล้านโทเคน ไม่มีอะไรถูกเก็บเป็น "ข้อเท็จจริง" หรือ "กฎ" เลย ทุกอย่างที่โมเดลรู้เป็นผลพลอยได้จากการเก่งขึ้นในการทาย ผลตามมาสองข้อ: เทรนจบ ณ จุดหนึ่งจึงมี knowledge cutoff และเทรนไม่ใช่สิ่งที่ทำได้ตามใจ — ถ้าโมเดลไม่รู้จัก API ภายในของเรา ทางแก้ไม่ใช่ "สอนมันซะ" แต่คือยัด context ให้

Inference

การรันโมเดล — การเอาโมเดลที่เทรนแล้วมาสร้างคำตอบ พารามิเตอร์ไม่ขยับเลย

ทำไมต้องรู้
ทุกครั้งที่คุยคือ inference — โมเดลไม่ได้ 'เรียนรู้' จากที่คุยกับเรา
อ่านเต็ม

การรันโมเดลที่เทรนเสร็จแล้วเพื่อสร้างคำตอบ เกิดขึ้นทุกครั้งที่มีการเรียกโมเดล พารามิเตอร์คงที่ ไม่เปลี่ยนแปลง โมเดลแค่ทายโทเคนถัดไปจาก context ที่ได้รับ ถูกกว่าการเทรนมาก แต่คิดเงินต่อโทเคน และเป็นค่าใช้จ่ายหลักของการใช้งานจริง ไม่มีอะไรที่ทำตอน inference ย้อนกลับไปแก้พารามิเตอร์ได้ — นี่คือเหตุผลที่แก้ไขวันนี้แล้ววันพรุ่งนี้มันลืม โมเดลไม่ได้เพิกเฉยคำแก้ไข มันแค่ไม่มีความสามารถเรียนรู้จากบทสนทนาเลย ความต่อเนื่องต้องมาจากภายนอก คือ context window หรือ memory system กลไกนี้ยังอธิบายบิลด้วย: ทุกคำขอรันโมเดลทับ context ทั้งก้อน ค่าใช้จ่ายจึงแปรตามทั้ง input และ output tokens และหนึ่งเทิร์นที่เรียก tool หลายรอบก็จ่ายค่า inference ทุกรอบ

Effort

ระดับการคิด — ปุ่มปรับว่าให้โมเดลคิดมากแค่ไหนก่อนตอบ คิดมาก = เปลืองโทเคนขาออกมากขึ้น

ทำไมต้องรู้
งานง่ายเปิด effort สูงคือเผาเงินเปล่า งานยากเปิดต่ำคือได้คำตอบมั่ว
อ่านเต็ม

ปุ่มปรับปริมาณการคิดของโมเดลก่อนตอบ ตั้งค่าต่อการเรียกโมเดลหนึ่งครั้ง ควบคุมความยาวของ "การคิด" ที่โมเดลทำก่อนเริ่มเขียนคำตอบที่เราเห็น การคิดนั้นถูกสร้างตอน inference เหมือนกัน harness มักซ่อนไม่ให้เห็น แต่เป็นงานจริงที่โมเดลทำ effort สูงกินเงินและช้ากว่า เพราะการคิดถูกส่งออกเป็น output tokens แม้เราไม่เห็นก็คิดเงิน ระดับทั่วไป: ต่ำ = แก้ไขจักรกล งานที่มีทางเดียวชัดเจน, กลาง = งานเขียนโค้ดทั่วไป (ดีฟอลต์), สูง = บั๊กยาก การตัดสินใจเชิงออกแบบ, สูงสุด = ปัญหายากที่สุดที่ตอบผิดแล้วแพง ตั้งต่ำเกินไปกับปัญหายากจะได้คำตอบมั่นใจแต่ตื้น ตั้งสูงสุดกับงานเปลี่ยนชื่อบรรทัดเดียวคือรอเปล่า ๆ ให้ปรับตามความยากของงานตรงหน้า ไม่ใช่ตาม session

Token

โทเคน — หน่วยเล็กสุดที่โมเดลอ่านและเขียน ประมาณขนาดคำแต่ไม่เท่ากันเป๊ะ

ทำไมต้องรู้
ทั้งขนาด context ราคา และความช้า วัดกันด้วยโทเคนทั้งหมด
อ่านเต็ม

หน่วยเล็กสุดที่โมเดลอ่านและเขียน ขนาดประมาณคำแต่ไม่เป๊ะ คำทั่วไปเป็นหนึ่งโทเคน คำแปลกหรือยาวถูกตัดเป็นหลายโทเคน ข้อความถูกแปลงเป็นโทเคนผ่าน tokenizer ซึ่งมีคลังคำหลักหมื่นชิ้นที่เรียนรู้ไว้ก่อนเทรน โมเดลไม่เห็นตัวอักษรหรือคำเลย เห็นแต่ลำดับโทเคน กฎง่าย ๆ คือหนึ่งโทเคนราวสามในสี่ของคำอังกฤษหนึ่งคำ โค้ดคาดเดายากกว่า: keyword ทั่วไปแปลงกระชับ แต่ hash, base64, ชื่อตัวแปรที่ generate มา จะถูกตัดเป็นโทเคนเยอะมาก ไฟล์เล็ก ๆ ที่เต็มไปด้วย string แปลก ๆ จึงอาจกิน context มากกว่าที่คิด ทุกอย่างวัดเป็นโทเคนหมด: ราคา ความเร็ว (โทเคน/วินาที) และขนาด context window

Next-token prediction

การทายคำถัดไป — สุ่มคำถัดไปจาก context ต่อท้าย แล้วรันใหม่ วนแบบนี้ไปเรื่อย ๆ

ทำไมต้องรู้
รู้กลไกนี้แล้วจะเข้าใจว่าทำไมโมเดลถึงมั่นใจแม้ตอนที่มันผิด
อ่านเต็ม

สิ่งที่โมเดลทำจริง ๆ อย่างเดียว: รับ context มา สุ่มเลือกโทเคนถัดไปหนึ่งตัว ต่อท้าย แล้วรันใหม่ ทุกเอาต์พุตไม่ว่าจะเป็นประโยค tool call หรือไฟล์พันบรรทัด ถูกสร้างทีละโทเคนแบบนี้ทั้งหมด แต่ละสเต็ปทำงานเหมือนกัน: โทเคนใน context window ถูกคำนวณผ่านพารามิเตอร์ ได้ความน่าจะเป็นของทุกโทเคนในคลังคำ แล้วสุ่มเลือกหนึ่งตัว การสุ่มนี้เองคือที่มาของ non-determinism ไม่ใช่บั๊ก แต่เป็นกลไกโดยตรง โมเดลไม่เคยเช็คว่าโทเคนที่จะพูด "จริง" ไหม เช็คแค่ว่า "น่าจะ" ไหม นี่คือรากของ hallucination และเพราะมันต้องผลิตทีละโทเคน ความเร็วในการสร้างคำตอบจึงเป็นเพดานตายตัวว่า agent จะทำงานได้เร็วแค่ไหน

Non-determinism

ผลลัพธ์ไม่คงที่ — อินพุตเดิมอาจได้เอาต์พุตต่างกัน เป็นธรรมชาติของทั้งการสุ่มคำและฝั่งผู้ให้บริการ

ทำไมต้องรู้
รันสองรอบได้ผลต่างกันเป็นเรื่องปกติ อย่าไปสรุปว่าแก้แล้วหายทั้งที่แค่บังเอิญ
อ่านเต็ม

อินพุตเดียวกันให้ผลลัพธ์ต่างกันได้ รันโมเดลสองครั้งด้วย context เดียวกันเป๊ะ อาจได้คำตอบคนละแบบ บางทีต่างแค่คำเดียว บางทีต่างทั้งแนวทาง ไม่ต้องแก้อะไรในโค้ดเลยก็เกิดได้ เป็นธรรมชาติของการสุ่มเลือกโทเคน (บางทีจงใจสุ่มเพื่อไม่ให้คำตอบซ้ำซากไร้คุณภาพ) บวกกับความแปรผันฝั่งผู้ให้บริการ (batch รวมกับ request อื่นบนฮาร์ดแวร์เดียวกัน ทำให้ตัวเลขทศนิยมคลาดเคลื่อนเล็กน้อยพอเปลี่ยนผลได้) ไม่มีปุ่มไหนปิดสิ่งนี้ได้ ควรคาดหวังผลลัพธ์กระจายบ้างในงานเดียวกัน — บางวันคมกริบ บางวันหลุดโฟกัส เป็นการสุ่มลูกเต๋าคนละดอกในงานเดิม ผลตามมาสองข้อ: ลองใหม่คือกลยุทธ์ที่ใช้ได้จริง (รอบที่ล้มเหลวคือหนึ่งในผลลัพธ์ที่เป็นไปได้ ลองใหม่อาจได้ดีกว่า) และการตรวจสอบสำคัญกว่าตอนใช้เครื่องมือ deterministic — เทสครั้งเดียวแล้วเชื่อว่าซ้ำได้เสมอไม่ได้ ต้องมี automated check คอยจับผลลัพธ์แย่ ๆ ตลอด

Model provider

ผู้ให้บริการโมเดล — คนที่รันโมเดลให้เรา ปกติอยู่ไกล (Anthropic, OpenAI, Google) หรือรันเองในเครื่องก็ได้ (Ollama)

ทำไมต้องรู้
ปัญหาช้า/ล่ม/quota ส่วนใหญ่อยู่ชั้นนี้ ไม่ใช่ที่โค้ดเรา
อ่านเต็ม

ผู้ที่รันโมเดลให้จริง ๆ ตอน inference ปกติเป็นบริการระยะไกล (Anthropic, OpenAI, Google) หรือรันในเครื่องตัวเองก็ได้ (Ollama, llama.cpp) harness เองไม่ได้รันโมเดล มันแค่ส่งคำขอไปให้ผู้ให้บริการทำ ผู้ให้บริการเป็นเจ้าของเครื่องจักรจริง พารามิเตอร์อยู่บนฮาร์ดแวร์ของเขา ทุกครั้งที่เรียกโมเดลคือ harness ส่งโทเคนผ่านเน็ตแล้วรอผลทายกลับมา ปัญหาหลายอย่างที่คนมักโทษโมเดลหรือ harness จริง ๆ อยู่ชั้นนี้: rate limit, ความจุลดลง, เซิร์ฟเวอร์ล่ม เวลา agent ค้างกลางทางหรือ error ทุกเทิร์น ควรเช็คหน้าสถานะของผู้ให้บริการก่อนเลย ผู้ให้บริการยังกำหนดราคาต่อโทเคน ส่วนลดแคช และโมเดลไหนใช้ได้บ้าง ผู้ให้บริการกับผู้สร้างโมเดลอาจเป็นคนละบริษัทก็ได้ (Bedrock, Vertex, OpenRouter เสิร์ฟโมเดลของคนอื่น)

Harness

ตัวครอบโมเดล — ทุกอย่างรอบโมเดลที่ทำให้มันกลายเป็น agent — tools, system prompt, การจัดการ context, permission, hook

ทำไมต้องรู้
อัปเกรด harness มักได้ผลมากกว่าเปลี่ยนโมเดล
อ่านเต็ม

ทุกอย่างที่ห่อหุ้มโมเดลจนกลายเป็น agent: tools, system prompt, การจัดการ context window, สิทธิ์การอนุญาต, hook ต่าง ๆ ตัวโมเดลเองทำได้แค่รับข้อความเข้าแล้วคายข้อความออก อ่านไฟล์เองไม่ได้ รันคำสั่งเองไม่ได้ จำเทิร์นก่อนหน้าเองไม่ได้ — harness เป็นคนจัดหาทั้งหมดนี้ให้: ประกอบ context ในแต่ละครั้งที่เรียกโมเดล รัน tool call ที่โมเดลขอ ป้อนผลกลับเข้าไป เก็บประวัติ session ถามสิทธิ์ก่อนทำอะไรเสี่ยง และตัดสินใจว่าเมื่อไหร่ควร compact ลูปของ agent (โมเดลเสนอ → harness รัน → ทำซ้ำ) คือ harness เป็นคนขับ นี่สำคัญตอนวินิจฉัยปัญหา: พฤติกรรมต่างกันระหว่างสองโปรดักต์ หรือระหว่างเมื่อวานกับวันนี้ มักไม่ใช่เพราะโมเดลเปลี่ยน แต่ harness เปลี่ยน — system prompt ต่างกัน ชุด tool ต่างกัน ค่าสิทธิ์เริ่มต้นต่างกัน กลยุทธ์จัดการ context ใหม่ ล้วนเปลี่ยนพฤติกรรมได้โดยโมเดลไม่ขยับเลย ไฟล์อย่าง AGENTS.md ก็เป็นคำสั่งถึง harness ไม่ใช่ถึงโมเดลโดยตรง

Model provider request

หนึ่งรอบเรียกโมเดล — หนึ่งรอบไป-กลับระหว่าง harness กับผู้ให้บริการ ส่ง context ไป ได้คำตอบกลับหนึ่งชุด

ทำไมต้องรู้
หน่วยนับเงินและนับเวลาจริงอยู่ตรงนี้ ไม่ใช่ 'ต่อข้อความ'
อ่านเต็ม

หนึ่งรอบไป-กลับระหว่าง harness กับผู้ให้บริการโมเดล harness ส่ง context ปัจจุบันไป ผู้ให้บริการตอบกลับหนึ่งอย่าง (tool call หรือคำตอบสุดท้าย) หนึ่งข้อความจากผู้ใช้อาจก่อให้เกิดการเรียกแบบนี้หลายรอบ ถ้า agent เรียก tool หลายตัว — ทุก tool result จะกระตุ้นให้เรียกรอบใหม่อีกครั้ง แต่ละรอบแบกทุกอย่างไปด้วย: system prompt บทสนทนาทั้งหมด ผลจาก tool ทุกตัว โมเดลไม่มีสถานะค้าง ผู้ให้บริการจึงไม่จำอะไรระหว่างรอบเลย รอบที่สี่สิบส่งซ้ำสิ่งที่รอบสามสิบเก้าส่งไปแล้วบวกผลลัพธ์ใหม่หนึ่งอัน (prefix cache มีไว้ทำให้การส่งซ้ำนี้ไม่แพงเกินไป) หน่วยคิดเงินก็อยู่ที่นี่ ไม่ใช่ที่ "หนึ่งข้อความ" — หนึ่งเทิร์นง่าย ๆ อย่าง "แก้เทสที่พัง" อาจกลายเป็นลูกโซ่ 6 รอบเรียก (รันเทส → อ่านไฟล์เทส → อ่านซอร์ส → แก้ไฟล์ → รันเทสอีกครั้ง → ตอบว่าผ่านแล้ว) เวลาสงสัยว่าโทเคนหายไปไหน ให้นับจำนวนรอบเรียก ไม่ใช่นับจำนวนเทิร์น

Input tokens

โทเคนขาเข้า — โทเคนที่ harness ส่งไปทุกรอบ คิดเงินถูกกว่าขาออก

ทำไมต้องรู้
context บวมทุกเทิร์น ค่าใช้จ่ายจึงโตแบบสะสม ไม่ใช่คงที่
อ่านเต็ม

โทเคนที่ harness ส่งไปทุกครั้งที่เรียกโมเดล — system prompt ประวัติบทสนทนา ผลจาก tool ทุกตัว ทุกอย่างที่โมเดลอ่านก่อนเขียนคำตอบ คิดเงินถูกกว่า output tokens เพราะประมวลผลง่ายกว่า เป็นค่าใช้จ่ายส่วนใหญ่ของงานเขียนโค้ดด้วย AI เพราะโมเดลไม่มีสถานะค้าง ทุกเทิร์นต้องส่ง session ทั้งก้อนซ้ำเป็น input — เทิร์นที่ห้าสิบแบก 49 เทิร์นก่อนหน้าไปด้วย การเรียกครั้งเดียวอาจสร้าง output แค่ไม่กี่ร้อยโทเคน แต่ส่ง input ที่สะสมมาเป็นแสนโทเคน prefix cache ช่วยลดต้นทุนตรงนี้ (ประวัติที่ตรงกับคำขอก่อนหน้าคิดเงินถูกเป็น cache tokens) แต่ถ้าค่าใช้จ่ายยังหนักอยู่ ทางแก้คือลดสิ่งที่ต้องส่งซ้ำ — clear หรือ compact ระหว่างงาน

Output tokens

โทเคนขาออก — โทเคนที่โมเดลเขียนกลับมา คิดเงินแพงกว่าเพราะใช้การคำนวณมากกว่า

ทำไมต้องรู้
ให้ตอบยาวโดยไม่จำเป็นคือจุดที่บิลพุ่งเร็วที่สุด
อ่านเต็ม

โทเคนที่โมเดลเขียนกลับมา คิดเงินแพงกว่า input tokens มาก (ทั่วไปราวห้าเท่า) เพราะใช้การคำนวณมากกว่าในการสร้าง ทุกอย่างที่โมเดลเขียนถูกนับหมด: ข้อความที่อ่าน โค้ดที่ออก tool call และการ "คิด" แบบขยาย (extended thinking) ก่อนตอบ ข้อสุดท้ายนี้คนมักไม่รู้ตัว เพราะ reasoning tokens ถูกคิดเงินเป็น output แม้ harness มักไม่โชว์ให้เห็น เปิด effort สูงขึ้นก็ยิ่งใช้โทเคนพวกนี้มากขึ้น output tokens ยังเป็นตัวกำหนดความเร็วของ session ด้วย: โมเดลอ่าน input ได้เร็ว แต่สร้าง output ทีละโทเคน ฉะนั้นเทิร์นที่รู้สึกช้าส่วนใหญ่คือกำลังเขียนคำตอบยาว ไม่ใช่กำลังอ่านอินพุต ถ้า session แพงทั้งที่ input ไม่เยอะ ให้เช็คว่า agent กำลังเขียนไฟล์ทั้งไฟล์ใหม่แทนที่จะ patch เฉพาะจุดหรือเปล่า

Prefix cache

แคชส่วนหัว — ที่เก็บฝั่งผู้ให้บริการ ทำให้รอบถัดไปไม่ต้องประมวลผลส่วนต้นที่เหมือนเดิมซ้ำ

ทำไมต้องรู้
ทำไมการสลับ system prompt ไปมาถึงแพงกว่าที่คิด — มันทำแคชแตก
อ่านเต็ม

ที่เก็บฝั่งผู้ให้บริการ ทำให้คำขอที่ติดกันข้ามการประมวลผลส่วนต้นที่เหมือนกันซ้ำได้ ถ้าจุดเริ่มต้นของคำขอตรงกับคำขอก่อนหน้า (system prompt เดียวกัน ประวัติเดียวกันถึงจุดหนึ่ง) ผู้ให้บริการใช้ผลเดิมซ้ำแล้วคิดเงินส่วนนั้นถูกลงมากในฐานะ cache tokens คุ้มเพราะ session โตแบบต่อท้ายอย่างเดียว ทุกคำขอส่งประวัติทั้งหมดซ้ำเป็น input tokens และในสถานการณ์ปกติ ประวัติจะเปลี่ยนแค่ตอนท้าย — แต่ละคำขอคือคำขอก่อนหน้าบวกข้อความใหม่ไม่กี่บรรทัด ผู้ให้บริการประมวลผลส่วนต้นที่ยาวและซ้ำแค่ครั้งเดียว เก็บผลไว้ ไม่งั้น session ยาว 50 เทิร์นจะต้องจ่ายค่าประมวลผลเทิร์นแรกซ้ำ 50 รอบ แคชยังหมดอายุด้วย — ปกติไม่กี่นาที ถ้าปล่อย session ค้างนานเกินนั้นแล้วกลับมาใช้ใหม่ คำขอแรกจะแพงเต็มราคาอีกครั้งก่อนแคชจะกลับมาทำงาน ถ้าค่าใช้จ่ายพุ่งกลางทาง ให้สงสัยว่ามีอะไรเปลี่ยนที่จุดเริ่มต้นบทสนทนา เช่น harness แทรกเวลาปัจจุบันเข้า system prompt ทุกเทิร์น จนแคชแตกทุกครั้ง

Cache tokens

โทเคนจากแคช — โทเคนขาเข้าที่ผู้ให้บริการเคยประมวลผลไว้แล้ว คิดเงินถูกกว่ามาก

ทำไมต้องรู้
อ่านบิลแล้วเห็นตัวเลขนี้เยอะ = ระบบใช้แคชได้ดี ไม่ใช่ใช้เยอะเกิน
อ่านเต็ม

input tokens ที่ผู้ให้บริการเคยแคชไว้จากคำขอก่อนหน้า จึงไม่ต้องประมวลผลซ้ำ เมื่อคำขอติดกันมีส่วนต้นตรงกัน ผู้ให้บริการใช้งานเดิมซ้ำผ่าน prefix cache แล้วคิดเงินส่วนนั้นถูกกว่ามาก — คันโยกที่ทำให้ session ยาว ๆ ใช้งานได้จริงในราคาที่รับได้ ไม่งั้นทุกเทิร์นต้องจ่ายเต็มราคาสำหรับประวัติทั้งหมด ตัวอย่างง่าย ๆ: ส่ง "AB" ครั้งแรกไม่มีอะไรให้แคช, ส่ง "ABC" ครั้งถัดมา "AB" ถูกแคชไว้แล้ว จ่ายเต็มแค่ "C", แต่ถ้าแก้ "B" เป็น "X" กลายเป็น "AXCD" แคชจะตรงแค่ "A" ตัวเดียว ที่เหลือเสียแคชหมด แคชเปราะบางแบบนี้เอง — อะไรก็ตามที่เปลี่ยนตอนต้นบทสนทนา (harness จัดลำดับใหม่ ไฟล์เปลี่ยนรูปแบบ) ทำให้แคชพังจากจุดนั้นเป็นต้นไป ถ้าค่าใช้จ่าย session พุ่งแบบไม่มีเหตุผลชัด ให้เทียบ cache tokens กับ input tokens ในรายงานการใช้งาน — แคชพังจะโผล่ตรงนั้นก่อนเลย

โมเดลไม่มีความจำ ทุกอย่างที่มันรู้ในวินาทีนั้นอยู่ในกรอบเดียวชื่อ context window

Stateless

ไม่จำอะไรเลย — ไม่พาข้อมูลข้ามรอบ โมเดลเป็นแบบนี้ระหว่างรอบเรียก และ agent เป็นแบบนี้ระหว่าง session โดยดีฟอลต์

ทำไมต้องรู้
ความรู้สึกว่า 'มันจำได้' มาจาก harness ส่งประวัติไปให้ใหม่ทุกรอบ ไม่ใช่ความจำจริง
อ่านเต็ม

ไม่พาข้อมูลอะไรข้ามไปเลย โมเดลไม่มีสถานะค้างระหว่างการเรียกแต่ละครั้ง — ทุกคำขอต้องส่ง context window ทั้งก้อนใหม่ เพราะโมเดลไม่มีทางเห็นอะไรนอกจากนั้น agent เองก็ไม่มีสถานะค้างข้าม session โดยดีฟอลต์ — session ใหม่เริ่มจากว่างเปล่า ไม่มีร่องรอยของ session ก่อนหน้าเลย พารามิเตอร์แช่แข็งหลังเทรน ไม่มีอะไรที่ทำตอน inference เปลี่ยนมันได้ โมเดลไม่ได้เรียนรู้จากคำแก้ไข ไม่จำว่าเคยถูกบอกเรื่องเดียวกันเมื่อวาน — ความรู้สึกต่อเนื่องระหว่างเทิร์นในหนึ่ง session เป็นสิ่งที่ harness สร้างขึ้นด้วยการเก็บ transcript แล้วส่งซ้ำทุกครั้ง โมเดลไม่ได้ "จำ" บทสนทนา มันแค่ "อ่านใหม่" ทุกรอบ ผลตามมา: ถ้าอยากให้อะไรถูกจำข้าม session ต้องเขียนมันลงที่ที่ agent จะอ่านกลับมาได้ เช่น AGENTS.md, memory system, หรือ handoff artifact

บริบท — ข้อมูลที่เกี่ยวข้องกับงานตรงหน้า ที่ agent เข้าถึงได้ ณ ตอนนี้

ทำไมต้องรู้
งานพังส่วนใหญ่ไม่ได้พังที่โมเดล แต่พังที่ context ไม่ครบหรือรกเกิน
อ่านเต็ม

ข้อมูลที่เกี่ยวข้องกับงานตรงหน้าที่ agent เข้าถึงได้ ณ ตอนนี้ เป็นคำนามนามธรรม ต่างจาก context window (ลำดับโทเคนจริงที่โมเดลเห็น) และต่างจาก session (ประวัติบทสนทนาที่สะสมไว้) — context คือ "สิ่งที่ agent รู้ที่เกี่ยวข้องกับงาน" การ "โหลดอะไรเข้า context" คือทำให้มันเป็นส่วนหนึ่งของชุดนี้ ส่วน "context engineering" คือศาสตร์การคัดสรรมัน ข้อสำคัญคือ context วัดที่คุณภาพ ไม่ใช่ปริมาณ — context window อาจเกือบเต็มแต่ context ยังแย่อยู่ (เต็มไปด้วยผล tool เก่าที่ไม่เกี่ยวกับงาน) หรือ context window เกือบว่างแต่ context ดีเยี่ยม (มีแค่นิยาม type ตัวเดียวที่งานต้องใช้) ความผิดพลาดประจำวันส่วนใหญ่สืบไปถึงเรื่อง context ทั้งนั้น — เวลา agent มั่วชื่อ API ขัดแย้งกับสิ่งที่เคยตัดสินใจไว้ หรือเดาโครงสร้างข้อมูล ให้ถามก่อนว่าตอนนั้น context มีอะไรอยู่ ปกติแล้วข้อเท็จจริงที่เกี่ยวข้องไม่เคยถูกโหลดเข้าไป หรือถูกฝังจนจมหายเพราะ attention degradation ทางแก้คือคัดสรร: โหลดสิ่งที่งานต้องใช้ กันสิ่งที่ไม่เกี่ยวออก

Context window

กรอบบริบท — ทุกอย่างที่โมเดลเห็นในหนึ่งรอบเรียก มีขนาดจำกัดและต่างกันตามโมเดล

ทำไมต้องรู้
นี่คือช่องเดียวที่โมเดลใช้รับรู้โลก อะไรไม่อยู่ในนี้ = ไม่มีอยู่จริงสำหรับมัน
อ่านเต็ม

ทุกอย่างที่โมเดลเห็นในการเรียกแต่ละครั้ง มีขนาดจำกัดขึ้นกับแต่ละโมเดล และเป็นช่องทางเดียวเท่านั้นที่โมเดลรับรู้อะไรได้เลย เป็นลำดับโทเคนหนึ่งเดียว: system prompt บทสนทนาที่ผ่านมา ผลจาก tool ทุกตัวที่ harness ป้อนกลับเข้าไป ถ้าอะไรอยู่ในลำดับนี้ โมเดลใช้มันได้ ถ้าไม่อยู่ โมเดลไม่รู้ว่ามันมีอยู่เลย — ไม่รู้จักโค้ดเบสของเรา ไม่รู้ไฟล์ที่แก้เมื่อวาน ไม่รู้คำสั่งที่ให้ไปสาม session ก่อน อะไรก็ตามนอกกรอบนี้ต้องถูกดึงเข้ามาก่อนผ่าน tool call ถึงจะมีผล เพราะมีขนาดจำกัด มันจึงเต็มได้ — ทุกเทิร์นเพิ่มเนื้อหาเข้าไปเรื่อย ๆ (ข้อความเรา คำตอบโมเดล ผลจาก tool) session ยาว ๆ จะชนเพดานสักวัน บังคับให้ compact หรือ clear และเพราะทุกอย่างในกรอบแข่งกันเอง โทเคนที่โหลดเข้ามาหนึ่งตัวคือที่ว่างที่หายไปหนึ่งช่องสำหรับส่วนที่เหลือ เนื้อหาที่ไม่จำเป็นก็ยังแย่งความสนใจของโมเดลอยู่ดี ท่าทีที่ใช้ได้จริงคือมองกรอบนี้เป็นงบประมาณ — โหลดแค่สิ่งที่งานต้องใช้ ที่เหลือปล่อยไว้ข้างนอก

Stateful

พาข้อมูลต่อได้ — จำข้อมูลข้ามรอบได้ session เป็นแบบนี้ข้ามเทิร์น ส่วน agent ต้องมี memory system ถึงจะข้าม session ได้

ทำไมต้องรู้
แยกให้ออกว่าอะไร 'จำได้จริง' กับอะไร 'ถูกโหลดกลับมาใหม่'
อ่านเต็ม

พาข้อมูลต่อไปได้ session พาข้อมูลต่อได้ข้ามเทิร์น — context สะสมไปเรื่อยตามที่ session ดำเนินไป ซึ่งเป็นสาเหตุที่ session ยาว ๆ ไหลเข้าสู่ dumb zone agent อาจถูกทำให้พาข้อมูลต่อได้ข้าม session ด้วยการเพิ่ม memory system ที่เขียนข้อมูลลงสภาพแวดล้อมแล้วโหลดกลับตอนเริ่ม session ใหม่ แต่โมเดลเองไม่เคยพาข้อมูลต่อได้เลย — ความต่อเนื่องที่ดูเหมือนมีอยู่ทั้งหมดคือ harness ป้อน context กลับเข้าไปซ้ำ ๆ ต่างหาก แต่ละชั้นเก็บสถานะด้วยวิธีต่างกัน: โมเดลไม่เคยเก็บเลย (พารามิเตอร์แช่แข็ง เห็นแค่สิ่งที่อยู่ในคำขอแต่ละครั้ง), session เก็บข้ามเทิร์น (harness ต่อทุกข้อความและผล tool เข้า context), harness เก็บข้าม session (ไฟล์ memory, AGENTS.md, handoff artifact — เขียนไว้แล้วโหลดกลับทีหลัง), สภาพแวดล้อมเก็บตลอดเวลา (ไฟล์อยู่ต่อไม่ว่า session จะรันอยู่หรือไม่) แต่ละชั้นสร้างความ stateful ด้วยการอ่านสิ่งที่เก็บไว้ในชั้นล่างซ้ำเท่านั้น ไม่มีสถานะไหนถูกเก็บในตัวโมเดลเองจริง ๆ เลย และสถานะที่พาไปไม่ได้ดีเสมอ — สมมติฐานผิดที่ตั้งไว้ต้นๆ ก็ถูกพาต่อไปด้วยเหมือนกัน clearing คือการจงใจทิ้งสถานะของ session แล้วเริ่มจากสิ่งที่เขียนบันทึกไว้แทน

Agent

เอเจนต์ — โมเดลที่ถูกติด tools, system prompt และ context window แล้วผลัดเทิร์นกับผู้ใช้ = โมเดลที่ขยับได้

ทำไมต้องรู้
แยกให้ชัดจาก 'โมเดล' เวลาสั่งงาน จะได้รู้ว่าต้องแก้ชั้นไหน
อ่านเต็ม

โมเดลที่ถูกห่อด้วย tools, system prompt และ context window แล้วผลัดเทิร์นกับผู้ใช้ — Claude Code เป็น agent, Cursor เป็น agent, Claude.ai เป็น agent สิ่งที่เราคุยด้วยจริง ๆ คือ agent มันคือโมเดลที่ถูกตั้งค่าให้ขยับได้เพื่อจุดประสงค์หนึ่ง ต่างจากคำอื่นในพจนานุกรมนี้ตรงที่ "agent" ไม่ได้ชี้ถึงชิ้นส่วนกลไกอะไรเลย โมเดลคือไฟล์พารามิเตอร์ harness คือซอฟต์แวร์ที่ชี้ไปได้ แต่ agent ไม่ใช่ทั้งสองอย่าง — มันคือหน่วยที่เราพูดด้วย คนมักทำให้ AI มีลักษณะเหมือนมนุษย์อยู่แล้ว และ agent คือหน่วยนั้น สิ่งที่เรามอบหมายงานให้ สิ่งที่อ่านข้อความเราแล้วตอบ คำว่า "มัน" ในประโยค "มันทำ build พังอีกแล้ว" พอพูดว่า agent ทำอะไรสำเร็จ หมายถึงโมเดลบวก harness ทำร่วมกัน แต่เรากำลังพูดถึงมันในฐานะตัวละครเดียว แนวคิดนี้เก่ากว่ากระแส AI รอบนี้มาก — software agent ที่รับมอบหมายเป้าหมายแล้วทำแทนเรา เป็นแนวคิดที่มีมานานพอ ๆ กับ AI เอง

System prompt

คำสั่งประจำตัว — คำสั่งที่ harness แปะไว้หน้าสุดของทุกรอบเรียก เป็นบรีฟถาวรของ agent

ทำไมต้องรู้
พฤติกรรมประหลาดที่เกิดทุกครั้ง มักมีรากอยู่ตรงนี้ ไม่ใช่ที่ข้อความล่าสุด
อ่านเต็ม

คำสั่งที่ harness แปะไว้หน้าสุดของทุกครั้งที่เรียกโมเดล — บรีฟถาวรของ agent ว่ามันคือใคร ควรทำตัวยังไง เรียก tool ไหนได้บ้าง ควรทำตามข้อตกลงอะไร ปกติค่อนข้างนิ่งตลอด session เขียนโดยผู้สร้าง harness ไม่ใช่โดยเรา และใน harness สำหรับเขียนโค้ดมักยาวมาก — บางทีนับหมื่นโทเคนของกฎพฤติกรรม คำอธิบาย tool และการจัดการกรณีพิเศษ ทั้งหมดถูกคิดเป็น input tokens ทุกเทิร์น คำสั่งของเราเองก็ขี่ไปด้วย — ไฟล์อย่าง AGENTS.md ถูกโหลดควบคู่กับ system prompt ตอนเริ่ม session โมเดลจึงอ่านบรีฟของผู้สร้าง harness กับของเราพร้อมกันก่อนเห็นข้อความของเราด้วยซ้ำ เพราะเหมือนเดิมทุกครั้ง มันจึงเป็นจุดเริ่มของ prefix cache ด้วย — ส่วนหนึ่งที่ harness ตรึงมันไว้คงที่ตลอด session แทนที่จะแก้ไปเรื่อย ๆ โมเดลถูกเทรนให้ให้ความสำคัญกับ system prompt เหนือข้อความผู้ใช้ ดังนั้นถ้า agent ยืนยันข้อตกลงบางอย่างที่เราไม่เคยขอ หรือจัดรูปแบบผลลัพธ์แบบที่สั่งเท่าไหร่ก็ไม่เปลี่ยน มักเป็นเพราะมันกำลังทำตาม system prompt อยู่ และข้อความของเรากำลังแพ้

Session

เซสชัน — การใช้งานหนึ่งช่วงที่มีขอบเขต เริ่มจากว่าง สะสมไปเรื่อย จบเมื่อเคลียร์ ปิด หรือถูกบีบเข้าเซสชันใหม่

ทำไมต้องรู้
เป็นหน่วยที่ควรวางแผนงานให้พอดี — งานใหญ่เกินหนึ่ง session ต้องมีแผนส่งต่อ
อ่านเต็ม

การใช้งานหนึ่งช่วงที่มีขอบเขตกับ agent เริ่มจากว่างเปล่า สะสมข้อความ ผลจาก tool และไฟล์ที่อ่านไปเรื่อย ๆ จบเมื่อถูก clear, ปิด หรือ compact เข้า session ใหม่ session คือสิ่งที่ "เติมเต็ม" context window — ถ้า context window คือกล่อง session คือสิ่งของที่ค่อย ๆ เติมกล่องนั้น งานที่ใหญ่เกินกว่าจะใส่ใน context window เดียวต้องแบ่งข้าม session ประวัติข้อความของ session คือความจำใช้งานของ agent โมเดลไม่มีสถานะค้าง ทุกอย่างที่ดูเหมือนมันจำได้ (ขอไปว่ายังไง เทสบอกอะไร ตัดสินใจอะไรไปสามเทิร์นก่อน) อยู่ในประวัติข้อความ ที่ถูกส่งซ้ำทุกครั้งที่เรียกโมเดล อะไรที่ไม่อยู่ใน session ไม่มีอยู่จริงสำหรับ agent เลย ความจำนี้จบพร้อมกับ session — session ใหม่เริ่มจากศูนย์ agent ที่รู้จักโค้ดเบสเราดีเมื่อวานนี้ ตอนเช้าไม่รู้อะไรเลย สิ่งที่รอดอยู่คือไฟล์ในระบบไฟล์ — ไฟล์ที่เขียนใน session หนึ่งอ่านได้ใน session ถัดไป ซึ่งเป็นสิ่งที่ handoff, memory system และ AGENTS.md อาศัยอยู่ เราเลือกได้ว่า session จะจบตรงไหน — ทุกอย่างใน session มีผลต่อทุกเทิร์นถัดไป งานที่ไม่เกี่ยวกันทำใน session เดียวกันจะทิ้งคราบไว้ให้คำตอบถัดไปเบี้ยว ทำหนึ่งงานต่อหนึ่ง session ช่วยให้ context ตรงประเด็น จบงานคือจุดธรรมชาติที่ควร clear

Turn

เทิร์น — หนึ่งข้อความของผู้ใช้ บวกทุกอย่างที่ agent ทำตอบกลับ จนกว่าจะคืนคิวให้ผู้ใช้

ทำไมต้องรู้
หนึ่งเทิร์นอาจมีการเรียกโมเดลหลายรอบ — เวลาคิดเงินอย่านับเป็นหนึ่ง
อ่านเต็ม

หนึ่งข้อความของผู้ใช้ บวกทุกอย่างที่ agent ทำตอบกลับ จนกว่าจะคืนคิวให้ผู้ใช้ ประกอบด้วยการเรียกโมเดลหนึ่งครั้งหรือมากกว่า — มากถ้า agent เรียก tool คำถามชวนคิดหนึ่งข้อปิดเทิร์น คำตอบของเราเปิดเทิร์นใหม่ ลำดับชั้นคือ session > เทิร์น > การเรียกโมเดลหนึ่งครั้ง สิ่งที่ทำให้เทิร์นน่าพูดถึงคือความยาวของมันเป็นการตัดสินใจของ agent ไม่ใช่ของเรา เราส่งข้อความเดียว agent ตัดสินใจเองว่าจะต่อ tool call กี่รอบก่อนจะคืนคิว เทิร์นหนึ่งอาจเป็นคำตอบประโยคเดียว หรือยี่สิบนาทีของการอ่าน แก้ไข รันเทส เป็นคุณสมบัติเดียวกันมองจากสองมุม: เทิร์นยาวคือสิ่งที่ทำให้งานแบบ AFK เป็นไปได้ และเทิร์นยาวก็เป็นจุดที่พลาดได้ง่ายเวลาไม่มีใครดู — กว่า agent จะคืนคิว มันอาจเบี่ยงไปไกลจากที่เราตั้งใจแล้ว เทิร์นยังเป็นหน่วยธรรมชาติสำหรับการบังคับทิศ — ทุกอย่างในเทิร์นเกิดขึ้นโดยไม่มีเรา ช่องว่างระหว่างเทิร์นคือจุดที่เราปรับทิศได้ harness ส่วนใหญ่ผ่อนปรนตรงนี้ — แทรกกลางเทิร์นเพื่อหยุดแล้วเปลี่ยนทิศได้ หรือพิมพ์ข้อความไว้ระหว่างที่มันทำงาน แล้วจะถูกอ่านเมื่อเทิร์นจบ ถ้าไม่ชอบผลลัพธ์ที่เทิร์นจบลงบ่อย ๆ ทางแก้มักคือขอเทิร์นที่เล็กลง — แผนก่อน แล้วค่อยทำทีละก้าว แลกความเป็นอิสระกับช่องว่างให้บังคับทิศบ่อยขึ้น

จัดสภาพแวดล้อมให้ดี ได้ผลมากกว่าเขียน prompt ยาว ๆ
อ่านเต็ม

โลกที่ agent ลงมือทำ — ทุกอย่างนอก harness ที่ agent รับรู้ผ่าน tool result และเปลี่ยนแปลงผ่าน tool call harness เป็นตัว "รัน" agent ส่วนสภาพแวดล้อมคือที่ที่ agent "ทำงานอยู่ข้างใน" ไฟล์อย่าง AGENTS.md อยู่ในสภาพแวดล้อม ส่วน harness คือตัวโหลดมันเข้า context window ระบบไฟล์เป็นสภาพแวดล้อมที่พบบ่อยที่สุด แต่ไม่ใช่แบบเดียว (ฐานข้อมูล, API ระยะไกล, session เบราว์เซอร์ ก็เป็นสภาพแวดล้อมได้เหมือนกัน) agent เห็นสภาพแวดล้อมเฉพาะตอนที่มันมอง — ทุกอย่างที่รู้เกี่ยวกับสภาพแวดล้อมมาจาก tool result ภาพที่มันมีจึงเป็นชุดภาพนิ่ง แต่ละภาพถูกต้อง ณ ตอนที่ถ่าย ถ้าไฟล์เปลี่ยนหลังจากที่ agent อ่านไปแล้ว (เราแก้เอง หรือ build step สร้างใหม่) agent จะยังคิดจากสำเนาเก่าจนกว่าจะมีอะไรกระตุ้นให้อ่านใหม่ agent ที่พูดถึงไฟล์อย่างมั่นใจทั้งที่มันไม่เหมือนเดิมแล้ว มักเป็นอาการนี้ — สภาพแวดล้อมขยับไปแล้ว แต่ภาพนิ่งไม่ได้ขยับตาม สภาพแวดล้อมยังเป็นชั้นเดียวที่คงอยู่เสมอ — context ของ session หายไปเมื่อ session จบ แต่ไฟล์ที่เขียนลงสภาพแวดล้อมยังอยู่ให้ session ถัดไปอ่าน ซึ่งเป็นสิ่งที่ memory system, handoff artifact และ AGENTS.md อาศัยอยู่ทั้งหมด เราเป็นคนกำหนดขนาดของสภาพแวดล้อม sandbox ทำให้มันเล็กลง จำกัดสิ่งที่ agent เข้าถึงได้ เพิ่ม tool ทำให้มันขยายออก ดึงฐานข้อมูลหรือ API เข้ามาในระยะเอื้อม

Filesystem

ระบบไฟล์ — ต้นไม้ของไฟล์และโฟลเดอร์ที่ agent อ่าน เขียน และรันคำสั่งอยู่ข้างใน

ทำไมต้องรู้
เป็นสภาพแวดล้อมมาตรฐานของ coding agent — โครงสร้างไฟล์ที่ดีคือ context ที่ดี
อ่านเต็ม

ต้นไม้ของไฟล์และโฟลเดอร์ที่ agent อ่าน เขียน และรันคำสั่งอยู่ข้างใน — สภาพแวดล้อมมาตรฐานของ coding agent AGENTS.md, skills, ซอร์สโค้ด, สคริปต์ build และการตั้งค่า tool ทั้งหมดอยู่ในระบบไฟล์ พอ harness บอกว่า "เริ่มในโปรเจกต์ของคุณ" มันคือชี้ agent ไปที่ระบบไฟล์นี้ agent แตะต้องมันได้เฉพาะผ่าน tool call เท่านั้น — อ่านไฟล์ เขียนไฟล์ รันคำสั่ง shell ไม่มีอะไรบนดิสก์อยู่ใน context window จนกว่า tool call จะโหลดมันเข้ามา นี่คือสิ่งที่ทำให้ agent ทำงานใน repo ที่ใหญ่กว่า context window มากได้ — ระบบไฟล์เก็บทุกอย่าง context เก็บแค่สิ่งที่งานปัจจุบันอ่านไปแล้ว บาง harness โหลดรายชื่อไฟล์ในไดเรกทอรีปัจจุบันเข้า context เป็นดีฟอลต์ (แค่ชื่อ ไม่ใช่เนื้อหา) ทำหน้าที่เป็น context pointer — agent เห็นว่ามีอะไรอยู่ แล้วอ่านไฟล์ที่ต้องใช้ มันยังเป็นพื้นที่ที่ใช้ร่วมกับเราด้วย — ไฟล์ที่ agent แก้คือไฟล์เดียวกับที่เราเปิดในเอดิเตอร์และดู diff ใน git ระบบไฟล์คือพื้นที่ทำงานร่วมที่เราใช้ตรวจสอบว่า agent ทำอะไรไป

Tool

เครื่องมือ — ฟังก์ชันที่ harness เปิดให้ agent เรียก เช่น Read, Write, Bash, Search

ทำไมต้องรู้
ความสามารถของ agent ถูกจำกัดด้วยชุด tool ที่มี ไม่ใช่ด้วยความฉลาดอย่างเดียว
อ่านเต็ม

ฟังก์ชันที่ harness เปิดให้ agent เรียกใช้ — Read, Write, Bash, Search เป็นวิธีเดียวที่ agent รับรู้และเปลี่ยนแปลงสภาพแวดล้อม: มันมองสภาพแวดล้อมไม่เห็นนอกจากผ่าน tool result และเปลี่ยนมันไม่ได้นอกจากผ่าน tool call การเรียก tool แต่ละครั้งเสียการเรียกโมเดลเพิ่มหนึ่งรอบ เพราะผลต้องกลับไปให้โมเดลก่อนจะตัดสินใจขั้นต่อไปได้ tool ที่ coding agent ส่วนใหญ่มีติดตัว: Read (คืนเนื้อหาไฟล์), Write (สร้างหรือแก้ไฟล์), Bash (รันคำสั่ง shell แล้วคืนผล), Search (หาไฟล์หรือข้อความที่ตรงรูปแบบทั่วโค้ดเบส) tool หนึ่งตัวประกอบด้วยสามอย่าง: ชื่อ คำอธิบายว่าทำอะไร และ schema ของพารามิเตอร์ harness ส่งนิยามพวกนี้ให้โมเดลทุกครั้งที่เรียก โมเดลเลือก tool ด้วยวิธีเดียวกับที่มันสร้างทุกอย่าง — โดยการเขียนโทเคน ในกรณีนี้คือ call ที่มีโครงสร้างพร้อมอาร์กิวเมนต์ โมเดลไม่เคยรันอะไรเองเลย harness เป็นคนอ่าน call รันฟังก์ชัน แล้วส่งผลกลับ รายการ tool กำหนดว่า agent ทำอะไรได้บ้าง โมเดลเก่งแต่ tool set แคบก็คือ agent แคบ — มันจะพยายามใช้ทุกอย่างผ่านสิ่งที่มีอยู่ ซึ่งเป็นเหตุผลที่ agent พึ่ง Bash หนักมาก เพราะ shell เป็น tool ตัวเดียวที่เข้าถึงระบบได้เกือบทุกอย่าง อยากให้ agent มีความสามารถใหม่แบบตรงจุด ให้เพิ่ม tool ให้มัน MCP คือมาตรฐานสำหรับเสียบ tool จากภายนอกเข้ามา นิยาม tool กินพื้นที่ context ทุกครั้งที่เรียก ดังนั้น tool set ใหญ่มีต้นทุนตั้งต้นก่อนจะเรียกใช้ด้วยซ้ำ และ tool ที่คำอธิบายคล้ายกันเยอะ ๆ ทำให้โมเดลเลือกผิดได้ง่ายขึ้น

Tool call

การสั่งใช้เครื่องมือ — เอาต์พุตของโมเดลที่ระบุชื่อ tool กับอาร์กิวเมนต์ — เป็นแค่ข้อความมีโครงสร้าง

ทำไมต้องรู้
โมเดลไม่ได้ 'รัน' อะไรเอง harness ต่างหากที่อ่านแล้วรันให้
อ่านเต็ม

เอาต์พุตของโมเดลที่ระบุชื่อ tool กับอาร์กิวเมนต์ เป็นแค่ข้อความมีโครงสร้าง มันไม่ทำอะไรเองเลย harness ต้องอ่านแล้วรันเอง ถูกสร้างโดยโมเดลในการเรียกโมเดลหนึ่งครั้ง วงจรของ tool call: (1) โมเดลรู้จัก tool ที่มีจากคำอธิบายใน system prompt (2) โมเดลปล่อย call ออกมา — ชื่อ tool บวกอาร์กิวเมนต์ มักเป็น JSON — แล้วหยุด (3) harness แปลผล call แล้วเช็คกับ permission mode (4) harness รันถ้าอนุญาต (5) harness ส่งผลลัพธ์กลับเป็น tool result ในการเรียกครั้งถัดไป หนึ่งเทิร์นของงาน agent มักเป็นหลายรอบไป-กลับแบบนี้ต่อกัน เพราะ call ถูกสร้างด้วย next-token prediction เหมือนเอาต์พุตอื่น ๆ มันผิดได้แบบที่โมเดลผิดได้ทั่วไป: path ที่ไม่มีอยู่จริง flag ที่คำสั่งไม่มี อาร์กิวเมนต์ที่ดูสมเหตุสมผลแต่ผิด harness รันตามที่เขียนไว้ ไม่ใช่ตามที่ตั้งใจ — path พิมพ์ผิดไม่ error สวย ๆ มันแก้ไฟล์ผิดไฟล์ไปเลย

Tool result

ผลจากเครื่องมือ — สิ่งที่ harness ส่งกลับหลังรัน — เนื้อไฟล์ เอาต์พุต หรือ error

ทำไมต้องรู้
เป็นมุมมองเดียวที่ agent มีต่อสภาพแวดล้อม ถ้าผลลัพธ์ตัดทิ้ง agent ก็ตาบอดตรงนั้น
อ่านเต็ม

สิ่งที่ harness ส่งกลับหลังรัน tool call — เนื้อไฟล์ ผลคำสั่ง หรือ error เป็นมุมมองเดียวที่ agent มีต่อสภาพแวดล้อม เดินทางกลับไปหาโมเดลในการเรียกโมเดลครั้งถัดไป ซึ่งโมเดลจะตัดสินใจว่าจะทำอะไรต่อ tool call กับ tool result คือปลายสองด้านของการแลกเปลี่ยนเดียวกัน อยู่ในเทิร์นเดียวกัน วงจร: harness รัน tool call (รันคำสั่ง อ่านไฟล์) → เก็บผลลัพธ์ (output เนื้อหา หรือ error) → ต่อท้ายเข้า context เป็นข้อความ → ส่ง context ทั้งหมดไปในการเรียกครั้งถัดไป → โมเดลอ่านผลแล้วตัดสินใจ: เรียก tool อีก หรือให้คำตอบสุดท้าย ผลลัพธ์นี้ค้างอยู่ใน context ตลอด session ที่เหลือ tool result มักเป็นส่วนใหญ่ของ context ใน coding session — ทุกไฟล์ที่อ่าน ทุกเทสที่รัน ทุกการค้นหา ลงเต็มและกินโทเคนต่อไปแม้จะหมดประโยชน์แล้ว ผลลัพธ์ก้อนใหญ่ไม่กี่ก้อน (log เทสที่ยืดยาว ไฟล์ generate ที่อ่านทั้งไฟล์) อาจดัน session เข้าใกล้ขอบ context window เร็วกว่าตัวบทสนทนาเองด้วยซ้ำ เพราะผลลัพธ์คือทั้งหมดที่โมเดลเห็น มันไม่มีทางเช็คสภาพแวดล้อมที่อยู่เบื้องหลังได้เลย ถ้า output ถูกตัดทอน คำสั่งล้มเหลวเงียบ ๆ หรือ harness คืน error แทนเนื้อหา โมเดลจะให้เหตุผลจากสิ่งที่ได้รับเท่านั้น เวลาภาพของ agent เกี่ยวกับระบบเราดูผิดเพี้ยน ให้ไปดูที่ tool result — ที่ไหนสักที่ใน transcript มีผลลัพธ์ที่บอกอะไรบางอย่างต่างจากที่เรารู้ว่าเป็นจริง

MCP

โปรโตคอลต่อเครื่องมือนอก — มาตรฐานสำหรับเสียบ tool server จากภายนอกเข้ากับ harness

ทำไมต้องรู้
ทางที่ agent จะได้ tool เกินกว่าที่ harness ให้มาตั้งแต่แรก
อ่านเต็ม

โปรโตคอลสำหรับเสียบ tool server จากภายนอกเข้ากับ harness — วิธีที่ agent ได้ tool เพิ่มนอกเหนือจากที่ harness มีติดตัวมาแต่แรก agent ไม่เคย "เรียก MCP" โดยตรง มันเรียก tool ตัวหนึ่ง แล้วบังเอิญว่า harness ได้ tool นั้นมาจาก MCP server ยังเปิดให้ resource (ข้อมูลอ่านอย่างเดียว) กับ prompt (เทมเพลตใช้ซ้ำ) ด้วย แต่การให้ tool คือการใช้งานหลัก โปรโตคอลนี้แก้ปัญหาการเชื่อมต่อ ถ้าไม่มีมาตรฐาน ทุก harness ต้องเขียนการเชื่อมต่อ Linear, Slack, ฐานข้อมูล แยกกันเอง มี MCP แล้วเขียนครั้งเดียวเป็น server แล้ว harness ที่รองรับ MCP ตัวไหนก็ใช้ได้หมด ต้นทุนอยู่ที่ context — ทุก tool ที่ server ประกาศมาในรูปนิยาม (ชื่อ คำอธิบาย schema พารามิเตอร์) โมเดลเรียกได้แค่ tool ที่มันรู้จัก วิธีตรงไปตรงมาคือโหลดทุกนิยามเข้า context window ตั้งแต่ต้น — ติดตั้ง server ใจกว้างสักไม่กี่ตัว session ก็เริ่มด้วยพันโทเคนของ tool schema ก่อนจะพิมพ์อะไรเลย เสียงบความสนใจไปกับ tool ที่งานไม่มีวันได้ใช้ harness หลายตัวเริ่มแก้ด้วย tool search — แทนที่จะโหลดนิยามเต็ม context เก็บแค่ context pointer ไปยัง tool ที่มี agent ค้นหาชื่อหรือจุดประสงค์แล้วโหลดนิยามเฉพาะตอนต้องใช้จริง ถ้า harness ไม่ทำแบบนี้ ต้นทุนตั้งต้นยังคงอยู่ คุ้มค่าที่จะเปิดเฉพาะ server ที่โปรเจกต์ต้องใช้จริง ๆ

Permission request

การขออนุญาต — สิ่งที่ harness แสดงให้ผู้ใช้ดูก่อนรัน tool call ที่ยังไม่ได้อนุมัติล่วงหน้า

ทำไมต้องรู้
เป็นกลไกจริงที่ทำให้มนุษย์ยังอยู่ในลูป — ไม่ใช่แค่คำสัญญาใน prompt
อ่านเต็ม

สิ่งที่ harness แสดงให้ผู้ใช้ดูก่อนจะรัน tool call ที่ยังไม่ได้อนุมัติล่วงหน้า โมเดลสร้าง tool call ขึ้นมา แทนที่จะรันทันที harness หยุดแล้วถาม อนุมัติก็รัน ปฏิเสธก็ส่งกลับไปเป็น tool result ให้โมเดล เป็นกลไกที่ harness ใช้ดึงมนุษย์เข้าไปอยู่ในลูปสำหรับการกระทำที่เสี่ยงหรือละเอียดอ่อน วงจร: (1) โมเดลสร้าง tool call (2) harness เช็คกับ permission mode และการอนุมัติที่บันทึกไว้ก่อนหน้า (3) ถ้าอนุมัติล่วงหน้าแล้วรันทันที ไม่งั้นหยุดแล้วโชว์คำขอ (4) ผู้ใช้อนุมัติครั้งเดียว อนุมัติตลอด session หรือปฏิเสธ (5) harness รัน call หรือส่งการปฏิเสธกลับเป็น tool result การปฏิเสธเป็นการบังคับทิศ agent ด้วย โมเดลอ่านการปฏิเสธเหมือน tool result ทั่วไปแล้วตอบสนอง — ลองวิธีอื่น หรือถามว่าเราต้องการอะไร harness ส่วนใหญ่ให้แนบข้อความไปกับการปฏิเสธได้ ทำให้คำขอกลายเป็นจุดบังคับทิศ: "ไม่ใช่แบบนั้น ใช้สคริปต์ migration แทน" มาถึงพอดีตอนที่โมเดลกำลังตัดสินใจขั้นต่อไป ต้นทุนคือทุกคำขอเป็นการรอแบบ synchronous ต่อเรา — agent ค้างอยู่จนกว่าเราจะตอบ ซึ่งโอเคตอนที่เรากำลังเฝ้าดู แต่เป็นปัญหาตอนไม่ได้เฝ้า agent ที่กระตุ้นคำขอตลอดเวลาไม่สามารถปล่อยให้ทำงานแบบ AFK ได้ permission mode คือปุ่มปรับ: call ไหนรันฟรี call ไหนต้องถามก่อน ยิ่งดีถ้ามี sandbox ทำให้ขยายชุดที่รันฟรีได้อย่างปลอดภัย

Permission mode

โหมดสิทธิ์ — ส่วนที่กำหนดว่า tool call แบบไหนต้องถาม แบบไหนรันได้เลย

ทำไมต้องรู้
เปิดกว้างเกินไป = เสี่ยง แคบเกินไป = ถูกถามจนทำงานไม่ได้
อ่านเต็ม

ส่วนที่กำหนดสิทธิ์ของ agent mode — tool call แบบไหนกระตุ้น permission request แบบไหนรันได้เลยอัตโนมัติ เป็นจุดประสงค์ดั้งเดิมของระบบโหมด ก่อนที่ harness จะเริ่มมัดรวมคำสั่งพฤติกรรมเข้าไปด้วย harness มักมีบันไดของโหมดเหล่านี้: อ่านอย่างเดียว/plan (อ่านอัตโนมัติ เขียนถูกบล็อก) ใช้สำหรับค้นคว้าวางแผนรีวิว, ดีฟอลต์ (อ่านอัตโนมัติ เขียนต้องถาม) ใช้ในงานประจำวันที่มีคนคุมอยู่, auto-edit (อ่านอัตโนมัติ แก้ไขอัตโนมัติ shell ต้องถาม) ใช้กับ repo ที่ไว้ใจแล้วหรืองานเชิงกลไก, "yolo"/full-auto (ทุกอย่างอัตโนมัติ) ใช้ใน sandbox หรืองาน AFK การเลือกขั้นบันไดคือการแลกระหว่างความปลอดภัยกับการถูกขัดจังหวะ ทั้งสองด้านผิดพลาดได้จริง ตั้งแน่นเกินไปเราจะกลายเป็นคอขวดเอง — agent หยุดทุกไม่กี่วินาทีเพื่อการอ่านที่ไม่เป็นอันตราย เรากดอนุมัติแบบไม่คิดจนคำอนุมัติหมดความหมาย (rubber-stamping คือแย่ที่สุดของทั้งสองแบบ ถูกขัดจังหวะเต็มที่แต่ไม่ได้ป้องกันอะไรเลย) ตั้งหลวมเกินไป agent จะแก้ไฟล์และรันคำสั่งที่เราอยากเห็นก่อนไปแล้ว ปลายด้านหลวมป้องกันได้ดีที่สุดเมื่ออยู่ใน sandbox ที่รัศมีความเสียหายถูกจำกัดไว้ นอก sandbox คนส่วนใหญ่ลงเอยที่อนุมัติการอ่านอัตโนมัติ แต่ยังคงมนุษย์ในลูปสำหรับอะไรที่ย้อนกลับไม่ได้

Agent mode

โหมดการทำงาน — ชุดสำเร็จรูปที่รวมโหมดสิทธิ์เข้ากับคำสั่งพฤติกรรมที่ยัดเข้า system prompt สลับกลางทางได้

ทำไมต้องรู้
เปลี่ยนโหมดคือเปลี่ยนทั้งความเสี่ยงและนิสัยของ agent พร้อมกัน
อ่านเต็ม

ชุดสำเร็จรูปที่กำหนดว่า agent ทำงานยังไงตอนรันจริง — มัดรวม permission mode เข้ากับคำสั่งพฤติกรรมที่ยัดเข้า system prompt ตัวอย่าง: ดีฟอลต์ที่ถามก่อนเรียกเสี่ยง, plan mode ที่บล็อกการแก้ไขและผลักดันให้ agent ไปทางค้นคว้า, accept-edits ที่อนุมัติการแก้ไขอัตโนมัติ, bypass permissions (เรียกกันเล่น ๆ ว่า YOLO mode) ที่อนุมัติทุกอย่างอัตโนมัติ สลับกลาง session ได้ สิ่งที่ทำให้โหมดต่างจากการตั้งค่าสิทธิ์เปล่า ๆ คือการมัดรวมนี้เอง permission mode เป็นแค่ประตู: ตัดสินว่า tool call ไหนผ่านได้ ประตูอย่างเดียวจะได้ agent ที่อยากแก้แต่แก้ไม่ได้ — มันเสนอเขียน โดนบล็อก แล้วลองวิธีอื่น คำสั่งที่แทรกเข้าไปตัดความอยากนั้นออก — plan mode ไม่ใช่แค่บล็อกการแก้ไข มันบอก agent ว่ากำลังอยู่ในช่วงวางแผน มันจึงอ่าน ถาม และเสนอแทนที่จะดันกับประตู ประตูกับการชี้นำชี้ไปทางเดียวกัน ในทางปฏิบัติ เราเปลี่ยนโหมดตามความไว้ใจที่เปลี่ยนไปตลอดงาน งานเดียวกันอาจผ่านหลายโหมด: plan mode ตอนกำลังคิดแนวทาง ดีฟอลต์ที่ถามก่อนสำหรับการแก้ไขจุดแรกที่ละเอียดอ่อน accept-edits เมื่อ agent แสดงให้เห็นแล้วว่าเข้าใจการเปลี่ยนแปลง bypass สำหรับงาน AFK ใน sandbox การเปลี่ยนโหมดไม่มีต้นทุน บทสนทนาต่อจากเดิมเป๊ะ แค่มีสิทธิ์ใหม่กับคำสั่งใหม่ ถ้าพบว่ากดอนุมัติทุกคำขอโดยไม่อ่านเลย โหมดตั้งแน่นกว่าความไว้ใจจริงของเรา ถ้าปฏิเสธการแก้ไขตลอด โหมดตั้งหลวมเกินไป

Sandbox

กล่องทราย — สภาพแวดล้อมแยกที่ agent รันอยู่ข้างใน — container, VM หรือ shell จำกัดสิทธิ์

ทำไมต้องรู้
จำกัดรัศมีความเสียหายตอนสั่งงานแบบไม่นั่งเฝ้า
อ่านเต็ม

สภาพแวดล้อมแยกที่ agent รันอยู่ข้างใน — container, VM, ระบบไฟล์ชั่วคราว หรือ shell จำกัดสิทธิ์ จำกัดรัศมีความเสียหายจากการกระทำของ agent แม้มันจะรันคำสั่งทำลายล้างหรือโหลดอะไรที่เป็นอันตรายมา ความเสียหายก็ถูกกักไว้ เป็นพื้นฐานความปลอดภัยที่ทำให้ AFK ใช้งานได้จริง sandbox กับ permission mode แก้ปัญหาเดียวกันจากคนละด้าน permission ถามก่อนที่การกระทำจะรัน sandbox จำกัดว่าการกระทำเอื้อมถึงอะไรได้ถ้ามันรันจริง permission ต้องการให้เราอยู่ในลูป — ทุกคำถามคือการขัดจังหวะ session ที่ถามตลอดแทบไม่เป็นอิสระเลย sandbox ใช้โครงสร้างพื้นฐานแทนความสนใจของเรา — ยิ่งแยกแน่นเท่าไหร่ ยิ่งต้องถามน้อยลงเท่านั้น ระดับการแยกมีหลายเกรด: shell จำกัดสิทธิ์ (จำกัดระดับ OS รอบแต่ละคำสั่ง กันการเขียนนอกโปรเจกต์และการเข้าถึงเน็ต), container (ระบบไฟล์ใหม่ ไม่มี credential ติดมา ทิ้งหลังใช้ กันทุกอย่างที่ agent ทำกับเครื่องตัวเอง), VM/cloud (เครื่องแยกต่างหากทั้งเครื่อง มักมาจาก harness กันแม้กระทั่งการหนีระดับ kernel) สิ่งที่ sandbox ไม่กันคือการกระทำที่ออกจากมันอย่างถูกกฎหมาย — agent ที่มี git credential ของเรา push ได้ agent ที่เข้าถึงเน็ตเรียก API production ได้ ต้องตัดสินใจก่อนว่าอะไรข้ามขอบเขตได้ ก่อนจะตัดสินใจว่าจะทำขอบเขตให้หนาแค่ไหน

Section 4

4 · รูปแบบความพัง

รู้จักอาการก่อน จะได้ไม่เสียเวลาแก้ผิดจุด

Sycophancy

อาการเออออ — เอาต์พุตที่เห็นด้วยอย่างมั่นใจ เกิดจากการเทรนที่ให้รางวัลคำตอบที่มนุษย์ชอบ

ทำไมต้องรู้
ถามว่า 'แบบนี้ถูกไหม' แล้วได้ 'ถูกครับ' ไม่ใช่หลักฐาน ต้องให้มันหาหลักฐานค้าน
อ่านเต็ม

เอาต์พุตที่เห็นด้วยอย่างมั่นใจ เกิดจากการเทรนที่ให้รางวัลคำตอบที่มนุษย์ชอบ และมนุษย์มักชอบการเห็นด้วยมากกว่าถูกบอกว่าผิด โมเดลจึงเรียนรู้ว่าการเห็นด้วยได้รางวัล แม้การเห็นด้วยนั้นจะผิดก็ตาม อาการที่พบ: ยอมแพ้เมื่อถูกดันกลับ (พลิกคำตอบที่ถูกอยู่แล้วเมื่อถามว่า "แน่ใจนะ?"), ชมแผนที่แย่ (บอกว่าแผนพังของเราเยี่ยมก่อนจะวิเคราะห์จริงด้วยซ้ำ), ตัดสินเอนเอียงตามกรอบที่ให้ (รีวิวดีขึ้นถ้าบอกว่าเราเขียนเอง แย่ลงถ้าบอกว่าคนอื่นเขียน ทั้งที่งานชิ้นเดียวกัน), เลียนแบบ (พูดความผิดพลาดของเรากลับมาเป็นการยืนยัน) วิธีทดสอบ: ถ้าไม่มีการชี้นำจากเรา มันจะพูดแบบนี้ไหม ถ้าสิ่งที่เปลี่ยนมีแค่โทนหรือกรอบที่เราให้ นั่นคืออาการเออออ ไม่ใช่การวิเคราะห์ที่เปลี่ยนจริง ทางแก้: ซ่อนความชอบของเราไว้ ตั้งคำถามแบบเป็นกลาง "รีวิวโค้ดนี้" ไม่ใช่ "โค้ดนี้ดีไหม" ระวังอย่าเรียกทุกคำตอบผิดที่บังเอิญถูกใจเราว่าเป็นอาการเออออ ถ้าไม่ผ่านการทดสอบข้างต้น คำนี้ก็ไม่ต่างจากคำว่า "ผิด" เฉย ๆ

Hallucination

อาการหลอน — เอาต์พุตผิดแต่มั่นใจ มีสองแบบ: แต่งข้อเท็จจริงขึ้นมาเอง กับหลุดจาก context ที่โหลดไว้

ทำไมต้องรู้
สองแบบนี้แก้คนละทาง แบบแรกต้องโหลดเอกสาร แบบสองต้องลด context ให้สะอาด
อ่านเต็ม

เอาต์พุตผิดแต่มั่นใจ มีสองแบบที่สาเหตุและทางแก้ต่างกัน — Factuality: แต่งข้อเท็จจริงเกี่ยวกับโลกขึ้นมาเอง (ฟังก์ชันที่ไม่มีอยู่จริง signature API ผิด อ้างอิงปลอม) สาเหตุคือช่องว่างของ parametric knowledge มักเป็นเรื่องหลัง knowledge cutoff ทางแก้คือโหลด contextual knowledge ที่ถูกต้องเข้าไป — Faithfulness: เอาต์พุตเบี่ยงจาก contextual knowledge ที่โหลดไว้ คำสั่งของผู้ใช้ หรือเหตุผลที่โมเดลเคยคิดไว้ก่อนหน้า สาเหตุคือ attention degradation แย่ลงเมื่ออยู่ใน dumb zone ทางแก้คือ clear หรือ compact next-token prediction สร้างเอาต์พุตที่ลื่นไหลไม่ว่าข้อเท็จจริงเบื้องหลังจะจริงหรือไม่ โมเดลไม่มีสัญญาณภายในบอกว่ามันไม่รู้อะไร วิธีที่แต่งขึ้นมาจึงมาในน้ำเสียงมั่นใจเหมือนวิธีที่ถูกต้อง โค้ดที่หลอนออกมาดูสมเหตุสมผลตั้งแต่ต้น เพราะมันคือรูปแบบที่ API ควรจะเป็นถ้ามันมีอยู่จริง ซึ่งเป็นสิ่งที่ทำให้มันรอดผ่านการรีวิวแบบผ่าน ๆ แล้วพังตอนรันจริงเท่านั้น ต้องรู้ว่ากำลังเจอแบบไหน เพราะทางแก้ของแบบหนึ่งทำให้อีกแบบแย่ลง Factuality คือความรู้ขาด ทางแก้คือเพิ่ม context — เอกสาร นิยาม type ไฟล์ Faithfulness คือความรู้มีอยู่แล้วแต่แพ้การแย่งความสนใจ ทางแก้คือลด context ถ้าวินิจฉัยผิดว่า faithfulness เป็น factuality แล้วยัดเอกสารเพิ่ม จะทำให้ context โตขึ้นและอาการเบี่ยงแย่ลงไปอีก เวลา agent ผิดอะไร เช็คก่อนว่าข้อมูลที่ถูกต้องอยู่ใน context อยู่แล้วหรือเปล่า ก่อนตัดสินว่าเจอปัญหาแบบไหน

Parametric knowledge

ความรู้ในตัวโมเดล — สิ่งที่โมเดลรู้จากการเทรน เก็บอยู่ในพารามิเตอร์ แช่แข็งไว้ตั้งแต่วันเทรน

ทำไมต้องรู้
อธิบายทั้งความเก่งฟรี ๆ และความมั่นใจผิด ๆ ในเรื่องที่เปลี่ยนไปแล้ว
อ่านเต็ม

สิ่งที่โมเดล "รู้" จากการเทรน เก็บอยู่ในพารามิเตอร์ แช่แข็งตั้งแต่วันเทรน โมเดลมองพารามิเตอร์ของตัวเองไม่ได้และแก้ไขเองไม่ได้ รายละเอียดหายไปตอนบีบอัด — ข้อเท็จจริงนับพันล้านถูกยัดใส่พารามิเตอร์จำนวนจำกัด เรื่องที่หายากจะเบลอ เป็นที่มาของความคล่องแคล่วในหัวข้อที่พบบ่อย และเป็นที่มาของการแต่งเรื่องในหัวข้อที่พบน้อย ความรู้แบบนี้ไม่ได้ถูกเก็บเป็นข้อเท็จจริงเลย การเทรนไม่เคยให้ฐานข้อมูลไว้ค้นหา มันแค่ปรับพารามิเตอร์จนโมเดลทายข้อความได้ดี และโมเดลที่ทายข้อความเรื่องหนึ่งได้ดี ก็ทำตัวเหมือนรู้เรื่องนั้น ความน่าเชื่อถือของความรู้แปรตามความถี่ที่มันปรากฏในข้อมูลเทรน — หัวข้อที่มีตัวอย่างเป็นล้านจะถูกผลิตซ้ำได้แม่นยำ หัวข้อที่มีแค่หยิบมือ โมเดลจะเดาจากสิ่งที่คล้ายกัน การผลิตซ้ำกับการเดาเป็นกระบวนการเดียวกันสำหรับโมเดล มันแยกไม่ออกว่ากำลังทำอันไหนอยู่ คำตอบที่แต่งขึ้นมาจึงมาด้วยความคล่องแคล่วเท่ากับคำตอบที่ถูก hallucination คือโมเดลเดาผิด ความรู้แบบนี้ยังเก่าลงได้ด้วย พารามิเตอร์หยุดเปลี่ยนที่ knowledge cutoff ไลบรารีที่ออกหรือเปลี่ยนชื่อหลังวันนั้นจึงไม่มีอยู่ในนั้นเลย และ API ที่เปลี่ยนไปแล้วจะถูกจำในรูปแบบเก่า ทั้งสองช่องว่าง (หายากเกินไปและใหม่เกินไป) แก้ด้วยวิธีเดียวกัน: เพิ่มพารามิเตอร์ไม่ได้ ต้องป้อนเป็น contextual knowledge แทน

Knowledge cutoff

วันตัดความรู้ — วันที่หลังจากนั้นโมเดลไม่มีความรู้ในตัวเลย

ทำไมต้องรู้
ไลบรารีหรือ API ที่ออกหลังวันนั้นคือกับดักการแต่งเรื่อง ถ้าไม่โหลดเอกสารจริงเข้าไป
อ่านเต็ม

วันที่หลังจากนั้นโมเดลไม่มี parametric knowledge เลย ไลบรารี API และเหตุการณ์หลังวันนั้นคือกับดักการแต่งเรื่อง เว้นแต่เอกสารของมันจะถูกโหลดเป็น contextual knowledge โมเดลแต่ละรุ่นมี cutoff ของตัวเอง cutoff เกิดขึ้นเพราะวิธีสร้างโมเดล: การเทรนอบข้อมูลตัวอย่างช่วงเวลาหนึ่งลงในพารามิเตอร์ แล้วหลังจากนั้นพารามิเตอร์ก็แช่แข็ง โมเดลไม่รู้ตัวว่าความรู้ของมันมีขอบ ถามเรื่องหลัง cutoff มันไม่ปฏิเสธ มันคาดคะเนจากสิ่งใกล้เคียงที่รู้แทน นั่นคือสิ่งที่ทำให้กับดักนี้เงียบ — โค้ดที่เขียนตาม library เวอร์ชันเก่าดูสมเหตุสมผล มัก compile ผ่าน แล้วพังเฉพาะส่วนที่เปลี่ยนไป ทางแก้เหมือนเดิมเสมอ: เอาข้อมูลปัจจุบันเข้า context โหลด changelog ชี้ไปที่นิยาม type ของเวอร์ชันที่ติดตั้งจริง หรือให้ agent อ่านเอกสารจากเว็บ อะไรก็ตามที่อยู่ใน context ชนะสิ่งที่ไม่มีอยู่ในพารามิเตอร์เสมอ

Contextual knowledge

ความรู้จากบริบท — ข้อเท็จจริงที่ agent อ่านได้จาก context ตรงหน้าเดี๋ยวนี้ คู่ตรงข้ามของความรู้ในตัวโมเดล

ทำไมต้องรู้
เป็นช่องทางเดียวที่เราแก้ความรู้ผิดของโมเดลได้จริง
อ่านเต็ม

ข้อเท็จจริงที่ agent อ่านได้ตรง ๆ จาก context ตอนนี้เลย — งานของผู้ใช้ ไฟล์ที่ agent อ่านเข้ามา tool result เนื้อหา AGENTS.md ที่โหลดตอนเริ่ม session คู่ตรงข้ามคือ parametric knowledge: parametric ถูก "เรียกความจำ" มาจากพารามิเตอร์ ส่วน contextual ถูก "อ่าน" จากกรอบ context ตรง ๆ hallucination พบน้อยกว่ามากตอน agent ทำงานจาก contextual knowledge เพราะคำตอบอยู่ตรงหน้ามันเลย ไม่ต้องขุดจากความจำเบลอ ๆ ในสองแบบของความรู้ มีแค่ contextual knowledge ที่เราคุมได้ พารามิเตอร์แช่แข็งแล้ว ทางเดียวที่จะให้โมเดลรู้อะไรที่มันไม่รู้ (SDK ภายใน ไลบรารีที่ออกหลัง cutoff การตัดสินใจเมื่อวาน) คือใส่มันลงใน context งานเขียนโค้ดด้วย AI ในทางปฏิบัติจำนวนมากลดรูปเหลือแค่นี้: เอาข้อเท็จจริงที่ถูกต้องมาอยู่ตรงหน้าโมเดลตอนที่มันต้องใช้จริง เวลาสองความรู้ขัดกัน contextual มักชนะ วางเอกสาร API ปัจจุบันลงไปแล้วโมเดลจะทำตามนั้นแทนความจำเก่าที่เบลอของ API เก่า — แม้เวอร์ชันเก่าจะแอบโผล่มาได้เหมือนกัน โดยเฉพาะลึกเข้าไปใน session ที่ยาว ถ้า agent ยังคงย้อนกลับไปใช้แพทเทิร์นเก่าทั้งที่โหลดเอกสารไว้แล้ว นั่นคือ parametric knowledge รั่วผ่าน contextual มา การพูดคำแก้ไขซ้ำหรือย้ายมันไปใกล้จุดทำงานมากขึ้นช่วยได้ ต่างจาก parametric, contextual knowledge มีต้นทุนในการใช้ ทุกอย่างที่โหลดเข้ากรอบเสียโทเคนและแย่ง attention budget ของโมเดล การโหลดเพิ่มจึงไม่ได้แปลว่าดีขึ้นเสมอไป — เป้าหมายคือข้อเท็จจริงที่เกี่ยวข้องอยู่ในกรอบ ไม่ใช่ทุกข้อเท็จจริง

Attention relationship

ความสัมพันธ์ระหว่างโทเคน — การจับคู่ระหว่างโทเคนสองตัว คู่ที่เกี่ยวข้องกันจะส่งอิทธิพลต่อกันมากกว่า context ขนาด N โทเคนมีคู่แบบนี้ราว N²

ทำไมต้องรู้
รากของทุกปัญหาเรื่อง context ยาวแล้วโง่ลง
อ่านเต็ม

ตอนทายแต่ละโทเคน โมเดลคำนวณโดยพิจารณาทุกโทเคนอื่นใน context ด้วย — บางตัวหนักมาก บางตัวแทบไม่มีผล การจับคู่ระหว่างโทเคนสองตัวคือ attention relationship คู่ที่มีความหมายเกี่ยวข้องกัน ("เธอ" กับ "สาระ" หรือการเรียก getUser() กับนิยาม function getUser ที่นิยามไว้) ส่งอิทธิพลต่อกันมากกว่าคู่ที่ไม่เกี่ยวข้อง context ขนาด N โทเคนมีความสัมพันธ์แบบนี้ราว N กำลังสอง คู่ความสัมพันธ์เหล่านี้คือที่ที่ "ความเข้าใจ" ที่ดูเหมือนของโมเดลอาศัยอยู่ ตอนมันแก้ปัญหาคำสรรพนาม เป็นเพราะความสัมพันธ์ระหว่าง "เธอ" กับ "สาระ" แข็งแรง ตอนมันเรียกฟังก์ชันด้วยอาร์กิวเมนต์ถูกต้อง เป็นเพราะความสัมพันธ์ระหว่างจุดเรียกกับนิยามที่อ่านไปก่อนหน้าทำงานอยู่ ไม่มีอะไรถูกค้นหาจากที่เก็บเลย ทุกอย่างถูกคำนวณสดใหม่ทุกครั้งที่เรียกโมเดล สำหรับทุกคู่ ตัวเลข N กำลังสองน่าคิดตาม เพราะมันโตเร็วกว่าที่สัญชาตญาณบอก — 1,000 โทเคนมีคู่ประมาณ 1 ล้าน, 10,000 โทเคนมีประมาณ 100 ล้าน, 100,000 โทเคนมีประมาณ 1 หมื่นล้าน แต่ละคู่ยังถูกคำนวณมากกว่าหนึ่งครั้งด้วย โมเดลมี attention head หลายหัว (จำนวนจริงของโมเดลระดับแนวหน้าไม่เปิดเผย แต่ห้าสิบถึงร้อยหัวเป็นตัวเลขที่พอเดาได้) แต่ละหัวคำนวณความสัมพันธ์เวอร์ชันของตัวเอง คู่ทุกคู่ในตารางข้างต้นจึงถูกทำซ้ำในทุกหัว มีแค่ความสัมพันธ์ส่วนน้อยเท่านั้นที่สำคัญกับงานตรงหน้าจริง ๆ คู่ระหว่างคำสั่งของเรากับโค้ดที่มันควบคุมเป็นหนึ่งในไม่กี่คู่ที่นับ ที่เหลือเกือบทั้งหมดในกลุ่มคือ noise และทั้งสองอย่างโตด้วยอัตราต่างกัน: ความสัมพันธ์ที่สำคัญคงที่โดยประมาณ แต่กลุ่มทั้งหมดโตแบบยกกำลังสองตามขนาด context ที่ 1,000 โทเคน คู่ที่เราสนใจคือหนึ่งในล้าน ที่ 100,000 โทเคน มันคือหนึ่งในหมื่นล้าน นี่คือเลขคณิตเบื้องหลัง attention budget และ attention degradation คือความรู้สึกตอนที่ความสัมพันธ์สำคัญได้ส่วนแบ่งบางเกินไป

Attention budget

งบความสนใจ — โทเคนแต่ละตัวมีอิทธิพลจำกัดให้แจกจ่ายไปยังโทเคนอื่น และไม่ได้เพิ่มขึ้นเมื่อ context โตขึ้น

ทำไมต้องรู้
ยัดข้อมูลเพิ่มไม่ได้แปลว่าเข้าใจมากขึ้น มันแค่เจือจางลง
อ่านเต็ม

โทเคนแต่ละตัวมีอิทธิพลจำกัดให้แจกจ่ายไปทั่ว context ที่เหลือ อิทธิพลหนักไปที่ความสัมพันธ์หนึ่งคู่ ทำให้เหลือน้อยลงสำหรับคู่อื่น งบนี้คิดต่อโทเคนและไม่โตขึ้นเมื่อ context โตขึ้น ซึ่งเป็นเหตุผลที่ session ยาว ๆ ยิ่งเจือจาง มองมันเป็นสัญญาณกับสัญญาณรบกวน คำสั่งของเราคือสัญญาณระดับเสียงคงที่ ทุกโทเคนอื่นใน context window คือเสียงแข่งขัน คำสั่งไม่เคยเบาลง มันยังอยู่ตัวอักษรครบเหมือนเดิม แต่พอ context โตขึ้น ห้องก็ดังขึ้นรอบตัวมัน อัตราส่วนสัญญาณต่อเสียงรบกวนจึงตกลง คำสั่งที่เคยดังที่สุดตอน context 10,000 โทเคน กลายเป็นเสียงพื้นหลังตอน 150,000 โทเคน นี่คือกลไกเบื้องหลัง attention degradation — โมเดลไม่ได้ลืม สัญญาณแค่จมหายในเสียงรบกวน อาการที่ปรากฏอ่านเหมือนการดื้อ agent เห็นด้วยกับข้อจำกัดตอนต้นแล้วค่อย ๆ เบี่ยงออกไป การแปะข้อจำกัดซ้ำช่วยได้แค่ชั่วคราว สาเหตุไม่ได้อยู่ที่คำสั่ง แต่อยู่ที่ทุกอย่างอื่นใน window ที่กำลังแข่งกับมัน สิ่งที่เราควบคุมได้คือสิ่งที่ใส่เข้า context เนื้อหาที่ไม่ช่วยงานไม่ได้เป็นกลาง มันคือ noise ทับทุกอย่างที่ช่วย ให้ window เล็กไว้ clear เมื่อ context ที่สะสมไม่คุ้มค่าอีกต่อไป และย้ำข้อจำกัดที่สำคัญซ้ำ แทนที่จะเชื่อว่าการพูดครั้งแรกจะยังคงอยู่

Attention degradation

ความสนใจเจือจาง — พอ session ยาวขึ้น งบความสนใจของแต่ละโทเคนถูกกระจายไปยังคู่แข่งมากขึ้น สัญญาณจึงอ่อนลง

ทำไมต้องรู้
อาการ 'คุยยาวแล้วลืมที่สั่งไว้ตอนต้น' มีที่มาเชิงกลไก ไม่ใช่นิสัย
อ่านเต็ม

พอ session โตขึ้น attention budget ของแต่ละโทเคนถูกกระจายไปทั่วคู่แข่งที่มากขึ้น สัญญาณของความสัมพันธ์ที่มีความหมายหดลง noise จาก context ที่ไม่เกี่ยวข้องแทรกเข้ามา โมเดลเดิม พารามิเตอร์เดิม แค่มีปากมากขึ้นที่ต้องแบ่งจากจานเดียวกัน เป็นสาเหตุของปรากฏการณ์ smart zone / dumb zone มันแสดงอาการเป็นโมเดลแย่ลงกลาง session — ข้อจำกัดที่ทำตามมาชั่วโมงหนึ่งเริ่มหลุด ถามซ้ำสิ่งที่เคยบอกไปแล้ว เขียนโค้ดที่ไม่สนใจไฟล์ที่อ่านไปก่อนหน้า ไม่มีอะไรเปลี่ยนที่ตัวโมเดลเลย ตัวแปรเดียวคือปริมาณ context ที่มันต้องให้ความสนใจตอนนี้ มันค่อยเป็นค่อยไป ซึ่งเป็นสิ่งที่ทำให้จับได้ยากจากในตัว session เอง ไม่มี error ไม่มีเกณฑ์ชัดเจน แต่ละเทิร์นแย่กว่าเทิร์นก่อนแค่นิดหน่อย พอเห็นชัดว่าหลุดแล้วก็อยู่ใน dumb zone มาสักพักแล้ว ฟื้นตัวด้วยการเอา context ออก ไม่ใช่เพิ่มเข้าไป แปะคำสั่งที่ถูกมองข้ามซ้ำเข้าไปแค่เพิ่มคู่แข่งอีกตัวใน window ที่แน่นอยู่แล้ว ช่วยได้แค่ชั่วคราว วิธีที่ได้ผล: clear แล้วโหลดกลับเฉพาะสิ่งที่งานต้องใช้ หรือ compact หรือ handoff ไปยัง session ใหม่ ให้มองการทำตามคำสั่งที่แย่ลงเป็นสัญญาณเรื่องความยาว context ไม่ใช่เรื่องความสามารถของโมเดล

งานสำคัญควรทำตอนหัวสด ไม่ใช่ท้าย session ที่ยาวมาแล้ว
อ่านเต็ม

ต้น session agent อยู่ใน "smart zone" — คมชัด โฟกัส จำแม่น พอ session โตขึ้นมันไหลเข้าสู่ "dumb zone" — สะเพร่าลง หลงลืมมากขึ้น ผิดพลาดมากขึ้น และเกิด faithfulness hallucination มากขึ้นด้วย โมเดลเดิม harness เดิม แค่ context มากขึ้น เป็นผลที่รู้สึกได้ของ attention degradation ในโมเดลระดับแนวหน้า dumb zone มักเริ่มราว 125,000-150,000 โทเคน แม้เรื่องนี้ยังถกเถียงกันอยู่ ให้ clear หรือ compact เมื่อ session บวม อย่าฝืนทำต่อ การเสื่อมนี้ค่อยเป็นค่อยไป ทำให้พลาดง่าย ไม่มีข้อความ error ไม่มีขอบเขตที่มองเห็น agent แค่เริ่มทำได้แย่ลงนิดหน่อยแล้วแย่ลงชัดเจนขึ้น สัญญาณที่พบบ่อย: ลืมคำสั่งที่ให้ไปยี่สิบเทิร์นก่อน ทำผิดซ้ำที่เคยแก้ไปแล้ว หรือยืนยันสิ่งที่ context ขัดแย้งอยู่อย่างมั่นใจ เพราะมันลื่นไถลแบบไม่มีรอยต่อ ปฏิกิริยาปกติคือฝืนทำต่อแล้วอธิบายซ้ำ ซึ่งยิ่งเพิ่ม context และทำให้แย่ลงไปอีก โซนพวกนี้ไม่ได้เดินตามขีดจำกัดของ context window เอง session อาจอยู่ลึกใน dumb zone ทั้งที่ window ยังว่างเหลือเยอะ — ขีดจำกัดคือจุดที่ harness ปฏิเสธไม่ทำต่อ แต่คุณภาพร่วงลงนานก่อนถึงจุดนั้นมาก ควรวางแผนตาม smart zone ไม่ใช่ตาม window — งบประมาณที่ใช้ได้จริงของงานคือโทเคนที่ agent ทำงานได้ดี ไม่ใช่โทเคนที่มันเก็บได้ทางเทคนิค smart zone คืองบประมาณ และงานที่ไม่เกี่ยวข้องก็ใช้งบนี้ไปด้วย ทุกงานที่ทำใน session หนึ่งใช้โทเคนไป การเริ่มงานที่สองใน session เดียวกันแปลว่าเริ่มมันใกล้ dumb zone มากขึ้น ทำหนึ่งงานต่อหนึ่ง session ให้แต่ละงานได้ใช้ช่วงที่คมที่สุดของ session เมื่องานหนึ่งใหญ่กว่าหนึ่ง smart zone ให้แบ่งมัน — handoff หรือ compact ที่จุดเปลี่ยนธรรมชาติ แล้วให้ session ใหม่ทำส่วนถัดไป

Section 5

5 · การส่งต่องาน

งานใหญ่เกินหนึ่ง session เสมอ ตัวชี้วัดคือของที่ส่งต่อไปอ่านรู้เรื่องหรือเปล่า

Clearing

ล้างเริ่มใหม่ — จบ session ปัจจุบันแล้วเริ่มใหม่ ข้อความถัดไปเริ่มจาก context ว่างเปล่า

ทำไมต้องรู้
วิธีที่ถูกที่สุดในการกลับเข้าช่วงหัวสด แต่แลกด้วยการเสียบริบททั้งหมด
อ่านเต็ม

จบ session ปัจจุบันแล้วเริ่มใหม่ ข้อความถัดไปเริ่มจาก session ว่างเปล่าและ context window ว่างเปล่า มักเป็นการตัดสินใจของผู้ใช้ Clearing คือยาแก้พิษของ context ที่ปนเปื้อน session สะสมทุกอย่าง: ความพยายามที่ล้มเหลว ทางที่ผิด tool result เก่าที่ไม่เป็นปัจจุบัน แผนที่ถูกล้มเลิก โมเดลอ่านทั้งหมดนี้ซ้ำทุกเทิร์น และประวัติแย่ ๆ ก็ถ่วงงานใหม่ไปด้วย ลึกเข้าไปใน session ที่ยาว agent จะคลุมเครือและดื้อขึ้น — คำสั่งที่ให้ไว้ชัดเจนถูกมองข้าม คุณภาพลื่นไถล กระตุ้นให้มันทำดีขึ้นก็ไม่ช่วย เพราะ noise ที่มันกำลังลุยอยู่ยังอยู่ใน context เดิม Clearing เอา noise นั้นออกไป การ clear ไม่ได้ลบบทสนทนาทิ้ง harness ส่วนใหญ่เก็บประวัติ session ไว้ในเครื่อง transcript ยังอยู่ให้อ่านหรือกลับมาต่อได้ สิ่งที่หายไปคือสถานะการทำงานของ agent โมเดลไม่มีสถานะค้าง session ใหม่จึงไม่รู้อะไรที่ session เก่ารู้เลย ถ้า session มีการตัดสินใจหรือความคืบหน้าที่ session ถัดไปต้องใช้ ให้ agent เขียน handoff artifact ก่อน แล้วเริ่ม session ใหม่ด้วยการชี้ไปที่มัน เทียบกับ compaction ที่สรุป session เข้า context ใหม่แทนที่จะเริ่มว่างเปล่า clearing คือเครื่องมือที่หยาบกว่า — ไม่มีอะไรพาต่อเลย รวมถึงขยะด้วย

Handoff

การส่งต่อ — ย้าย context จาก session หนึ่งไปอีก session โดยไม่มีทางกลับ วิธีขนย้ายมีหลายแบบ

ทำไมต้องรู้
คุณภาพงานรอบถัดไปขึ้นกับคุณภาพการส่งต่อ ไม่ใช่ความเก่งของรอบถัดไป
อ่านเต็ม

การย้าย context ของ agent จาก session หนึ่งไปอีก session หนึ่ง วิธีขนย้ายมีหลายแบบ — handoff artifact ที่เขียนไว้ สรุปในหน่วยความจำ (compaction) และอื่น ๆ ต่างจาก clearing (ไม่มีการย้ายอะไรเลย) เหตุผลที่ทำหลากหลาย: สลับบทบาท (นักวางแผน → ผู้ลงมือทำ) เริ่มงาน AFK แตกงานไปหลาย session พร้อมกัน หรือเคลียร์พื้นที่ context window session ที่รับจะเริ่มจาก context ว่างเปล่า โมเดลไม่มีสถานะค้าง ไม่มีอะไรจาก session เก่าที่มองเห็นได้จาก session ใหม่ สิ่งที่ session ถัดไปต้องใช้ต้องถูกขนย้ายอย่างชัดเจน ที่เหลือหายหมด "ไม่มีทางกลับ" คือข้อจำกัดที่กำหนดวิธีขนย้าย — session ใหม่ถามกลับ session เก่าว่าหมายความว่าอย่างไรไม่ได้ ฉะนั้นสิ่งที่ขนย้ายไปต้องยืนได้ด้วยตัวเอง เปรียบเทียบสองกลไก: handoff artifact เป็นไฟล์ในสภาพแวดล้อม อ่านและแก้ไขได้ก่อนที่อะไรจะพึ่งพามัน ใช้ซ้ำได้กับหลาย session ส่วน compaction เป็นสรุปใน context window เกิดอัตโนมัติและถูก แต่ตรวจสอบยากกว่า ป้อนให้แค่ session ถัดไปเดียว ความล้มเหลวของ handoff ที่แย่มองเห็นชัดคือการเถียงย้อนหลัง — session ใหม่เปิดประเด็นที่ตัดสินใจไปแล้วขึ้นมาใหม่ เพราะสิ่งที่ขนย้ายบันทึกแค่ผลตัดสินใจแต่ไม่มีเหตุผล ตัดสิน handoff ที่ดีจากสิ่งที่ session ที่ไม่มี context เลยทำอะไรกับมันได้

Primary source

แหล่งปฐมภูมิ — ตัวของจริง — โค้ด transcript ข้อมูลดิบ ครบและเชื่อถือได้ แต่แพงเวลาโหลดเข้า context

ทำไมต้องรู้
ตอนต้องพิสูจน์ ต้องกลับมาที่นี่เสมอ
อ่านเต็ม

แหล่งความจริงในรูปแบบดั้งเดิม — ตัวโค้ดจริง ประวัติบทสนทนาจริง log ดิบ การตอบกลับ API จริง ไม่ใช่คำบอกเล่าถึงสิ่งนั้น แต่คือตัวสิ่งนั้นเอง คู่ตรงข้ามคือ secondary source ถ้าอยากรู้ว่าโค้ดเบสเราทำอะไร ตัวโค้ดคือ primary source เอกสาร แผนภาพสถาปัตยกรรม และ README เป็นคำบรรยายถึงมัน ถูกต้อง ณ ตอนเขียน แต่หลังจากนั้นก็ตามความจริงไม่ทันตามตารางของตัวเอง เวลา agent ยืนยันอะไรที่ผิดเกี่ยวกับโปรเจกต์เราอย่างมั่นใจ คำถามคือมันทำงานจากแหล่งไหน — agent ที่อ่านเอกสารสืบทอดความล้าสมัยของเอกสารนั้นไปด้วย agent ที่อ่านโค้ดกำลังอ่านความจริงปัจจุบัน ต้นทุนคือสิ่งที่ทำให้ primary source ไม่ใช่ตัวเลือกดีฟอลต์ โหลดมันเข้า context window แพง — ไฟล์เต็ม transcript เต็ม ทุกโทเคนถูกคิดเป็น input และแย่งชิง attention budget สิ่งที่ได้แลกกับต้นทุนนั้นคือความครบถ้วน ไม่มีอะไรถูกกรองไว้ก่อนตามการตัดสินใจของคนอื่น สรุปที่เขียนเมื่อเดือนก่อนไม่สามารถมีรายละเอียดที่กลายเป็นสำคัญวันนี้ได้ แต่ primary source ยังมีอยู่ ใช้ primary source เมื่อความแม่นยำสำคัญ — signature ที่แท้จริง error จริง บรรทัดที่ throw จริง ส่วนใหญ่ของการจัดการ context คือการตัดสินใจว่าเมื่อไหร่ควรจ่ายต้นทุนเพื่อ primary source และเมื่อไหร่ secondary source ก็พอแล้ว

Secondary source

แหล่งทุติยภูมิ — คำบอกเล่าถึงของจริง ห่างออกมาหนึ่งชั้น — สรุป เอกสาร บทสรุปจากการบีบ context ถูกแต่ตกหล่นโดยธรรมชาติ

ทำไมต้องรู้
ประหยัดดี แต่ถ้าเถียงกันเรื่องข้อเท็จจริง อย่าใช้ตัวนี้ตัดสิน
อ่านเต็ม

คำบอกเล่าถึง primary source ที่ห่างออกมาหนึ่งชั้น — เอกสารที่บรรยายโค้ด สรุปที่บรรยาย transcript รายงานที่บรรยายผลการค้นหา ถูกกว่าที่จะโหลดเข้า context window เมื่อเทียบกับแหล่งที่มันบรรยาย และตกหล่นโดยธรรมชาติ: คนเขียนตัดสินใจว่าอะไรสำคัญ อะไรที่เขาทิ้งไปก็มองไม่เห็นสำหรับคนที่มีแค่สรุปนั้น งาน context engineering จำนวนมากคือการผลิต secondary source นี่แหละ compaction แปลงประวัติ session เป็นสรุปที่ใช้ตั้งต้น session ถัดไป subagent เผา context ของตัวเองไปกับการค้นหาที่รก แล้วคืนรายงานสั้น ๆ handoff artifact ย่อการตัดสินใจของ session ลงเป็นเอกสารให้ session ถัดไปอ่าน memory system กลั่นสิ่งที่ session เรียนรู้ลงเป็นโน้ต ทุกอย่างแลกแบบเดียวกัน: ความละเอียดแลกกับพื้นที่ว่าง secondary source พังได้สองแบบ: ตกหล่น (สรุป compaction ที่ทำการตัดสินใจเรื่อง schema หายไป รายงานที่ไม่ได้พูดถึง edge case) และล้าสมัย (primary source เปลี่ยนแต่คำบอกเล่าไม่ตามไป เอกสารเลยบรรยายสถาปัตยกรรมไตรมาสก่อนด้วยความมั่นใจของไตรมาสนี้) เมื่อ agent ทำงานจาก secondary source ที่พังแบบใดแบบหนึ่ง มันทำงานอย่างมั่นใจจากข้อมูลผิด ทางแก้คือส่งมันกลับไปที่ primary source ความล้มเหลวทั้งสองแบบไม่ได้แปลว่า secondary source เป็นความผิดพลาด context window มีจำกัดและ primary source แพง ถ้าไม่มีสรุป รายงาน และเอกสารส่งต่อ ของใหญ่ก็ไม่มีทางพอดี ทักษะคือรู้ว่ารายละเอียดไหนทนต่อการสูญเสียได้ และตรวจสอบกับ primary source เมื่อรายละเอียดไหนทนไม่ได้ secondary source ที่ทำดีควรมี context pointer ย้อนกลับไปต้นฉบับเสมอ

Handoff artifact

เอกสารส่งต่อ — เอกสารที่ใช้เป็นตัวขนย้ายการส่งต่อ เขียนโดย session หนึ่งเพื่อให้อีก session อ่าน

ทำไมต้องรู้
ถ้าเขียนไว้แล้วรอบหน้าอ่านไม่รู้เรื่อง เท่ากับไม่ได้ส่งต่อ
อ่านเต็ม

เอกสารที่ใช้เป็นตัวขนย้ายสำหรับ handoff — เขียนลงสภาพแวดล้อมโดย session หนึ่งเพื่อให้อีก session อ่าน spec, ticket และเอกสารแผนงาน ล้วนเป็น handoff artifact ทั้งนั้น เหตุผลที่ต้องเขียน: โมเดลไม่มีสถานะค้าง ไม่มีอะไรใน session รอดจากการ clear มันไป การตัดสินใจ ข้อจำกัด แผนที่ทำครึ่งทาง หายไปพร้อม context ที่เก็บมันไว้หมด สภาพแวดล้อมคงอยู่ การเขียนสถานะสำคัญลงไฟล์คือการย้ายมันไปที่ที่ session ถัดไปอ่านกลับมาได้ ตัวเอกสารคือ secondary source — คำบอกเล่าถึงงานของ session ไม่ใช่ตัวงานเอง นั่นทำให้มันเล็กพอที่จะบรีฟ session ใหม่ได้ และก็เป็นเหตุผลที่มันชวนหลงทางได้เหมือนกัน — มันบันทึกสิ่งที่ session ที่เขียนเชื่อ อะไรที่ตกหล่นหรือผิดจะมองไม่เห็นสำหรับคนอ่าน ตรงไหนที่คำกล่าวอ้างสำคัญ session ถัดไปควรตรวจสอบกับ primary source (โค้ด เทส) แทนที่จะรับมาเฉย ๆ เอกสารที่ดีเขียนขึ้นเพื่อให้อ่านเข้า session ที่ไม่มี context เลย ใช้ path ไฟล์ที่ชัดเจนแทน "ไฟล์ที่เราคุยกัน" บอกว่าตัดสินใจอะไรและทำไม เพื่อ session ถัดไปไม่ต้องเถียงเรื่องเดิมซ้ำ บอกว่าอะไรเสร็จแล้ว อะไรเหลืออยู่ ช่วยได้ถ้าบอก session ที่เขียนว่าเอกสารจะไปไหนต่อ: "เขียน handoff doc ให้ session ใหม่ที่ไม่รู้อะไรเกี่ยวกับงานนี้เลย" กลไกขนย้ายอีกแบบคือ compaction ที่สรุปในหน่วยความจำ เอกสารมีข้อได้เปรียบสองอย่าง: อยู่บนดิสก์ที่เราอ่านและแก้ไขได้ก่อนที่อะไรจะพึ่งพามัน และใช้ซ้ำได้ — spec เดียวกันบรีฟห้า session ขนานกันได้

เป็นตัวกันไม่ให้แต่ละ session ตีความเป้าหมายไปคนละทาง
อ่านเต็ม

handoff artifact ที่บรรยายงานหลาย session — สิ่งที่กำลังสร้าง ไม่ใช่แต่ละ session ทำส่วนของตัวเองยังไง เปลี่ยนแปลงไปตามงานที่ก้าวหน้า ประกอบขึ้นจาก ticket spec มีอยู่เพราะ session ใช้แล้วทิ้งได้ แต่งานใหญ่ไม่ใช่ อะไรที่ใช้ความพยายามเกินหนึ่ง context window ต้องมีที่อยู่นอก context — ที่ไหนสักที่ในสภาพแวดล้อมของ agent ที่รอดจากการ clear ไม่ว่าจะเป็นไฟล์ใน repo, GitHub issue หรือ issue tracker ที่ agent เข้าถึงได้ spec คือบ้านนั้น: เป้าหมาย ข้อจำกัด การตัดสินใจที่ทำมาแล้ว และรายการ ticket พร้อมสถานะ session ใหม่ตัวไหนก็อ่านแล้วรู้ว่างานอยู่ตรงไหนได้โดยไม่ต้องสืบทอด noise ที่สะสมมาจาก session ก่อน spec มีสไตล์ที่คุ้นเคยหลายแบบ ส่วนใหญ่สืบทอดจากวิธีที่ทีมงานเขียนบันทึกกันอยู่แล้ว product requirements document (PRD) เอนไปทางสิ่งที่ผู้ใช้เห็นและทำไม — ฟีเจอร์ พฤติกรรม เกณฑ์การยอมรับ design doc หรือ RFC เอนไปทางเทคนิค — แนวทางที่เลือก ทางเลือกที่ปฏิเสธ การแลกเปลี่ยน ที่ขนาดเล็กสุด plan.md ธรรมดาพร้อม checklist ของ ticket ก็ทำหน้าที่เดียวกันสำหรับฟีเจอร์หลาย session สไตล์สำคัญน้อยกว่าบทบาท สำหรับ agent ทุกอย่างเหล่านี้คือสิ่งเดียวกัน — คำแถลงเจตนาที่ยั่งยืนซึ่งมันอ่านตอนเริ่มทุก session

Ticket

ตั๋วงาน — เอกสารส่งต่อที่กำหนดขอบเขตงานหนึ่ง session อยู่เดี่ยว ๆ หรือห้อยใต้สเปกก็ได้ และบล็อกกันเองได้

ทำไมต้องรู้
หน่วยงานที่พอดีกับหนึ่ง session คือหน่วยที่ agent ทำจบได้จริง
อ่านเต็ม

handoff artifact ที่กำหนดขอบเขตงานหนึ่ง session อยู่เดี่ยว ๆ ได้ หรือห้อยใต้ spec เป็นลูกก็ได้ ticket บล็อกกันเองหรือถูกบล็อกโดย ticket พี่น้องได้ ลำดับงานจึงมาจากกราฟการพึ่งพา ไม่ใช่แผนเรียงเส้นตรง ข้อจำกัดหลักคือขนาด: หนึ่ง session ticket ควรทำเสร็จได้ก่อนที่ session จะหลุดออกจาก smart zone และข้อจำกัดนี้ทดสอบได้จริง ถ้า session บน ticket ของเราเสื่อมคุณภาพลงก่อนงานเสร็จเป็นประจำ แปลว่า ticket ใหญ่เกินไป ให้แบ่ง ถ้าแต่ละ session ใช้ context ส่วนใหญ่ไปกับการตั้งต้นก่อนจะทำงานจริงแค่ห้านาที แปลว่าเล็กเกินไป ให้รวมกัน ticket ที่ดีเขียนสำหรับคนอ่านที่ไม่มี context อื่นเลย มีเป้าหมาย เกณฑ์การยอมรับ และ context pointer ไปยังไฟล์และการตัดสินใจที่เกี่ยวข้อง มากพอที่ session จะเริ่มทำงานได้โดยไม่ต้องอนุมานสิ่งที่ session ก่อนหน้ารู้ใหม่ กราฟการพึ่งพายังเป็นตัวปลดล็อกความขนานด้วย ticket ที่เป็นอิสระต่อกัน (จุดใบของกราฟ) รันคนละ session พร้อมกันได้ เป็นวิธีที่ได้ผลจริงสำหรับการรันหลาย agent พร้อมกัน

Compaction

การบีบบริบท — การส่งต่อที่ทำในหน่วยความจำ: สรุปประวัติของ session เดิมไปตั้งต้น session ใหม่ ตกหล่นเสมอ แลกรายละเอียดกับพื้นที่ว่าง

ทำไมต้องรู้
หลังบีบแล้วรายละเอียดหาย ต้องรู้ว่าอะไรหายก่อนจะเชื่อคำตอบต่อจากนั้น
อ่านเต็ม

handoff ที่ทำในหน่วยความจำ: ประวัติของ session ก่อนหน้าถูกสรุป แล้วสรุปนั้นตั้งต้น session ใหม่ ตกหล่นโดยการออกแบบ — transcript คือ primary source สรุปคือ secondary source รายละเอียดถูกแลกกับพื้นที่ว่าง เกิดขึ้นได้ทั้งแบบผู้ใช้สั่งเอง หรืออัตโนมัติผ่าน autocompact กลไก: context window มีจำกัด และ session ยาว ๆ เติมมันจนเต็ม — ทุก tool result ทุกไฟล์ที่อ่าน ทุกทางที่ผิด อยู่ในประวัติทั้งหมด พอมันหนักขึ้น harness ขอให้โมเดลสรุป session ทิ้งประวัติดั้งเดิมไป แล้วตั้งต้น session ใหม่ด้วยสรุปนั้น อะไรที่ไม่ได้อยู่ในสรุปหายไปจาก context เลย บาง harness ผ่อนปรนตรงนี้ด้วยการเก็บ transcript เก่าไว้บนดิสก์ แล้วทิ้ง context pointer ไปยังมันในสรุป — secondary source เชื่อมกลับไปยัง primary source ของมัน รายละเอียดที่สรุปทำหายจึงกู้กลับมาได้ด้วยการอ่านต้นฉบับใหม่ สรุปถูกเขียนโดยโมเดล จึงสั่งมันได้ "เก็บการตัดสินใจเรื่อง schema ไว้" ทำให้สิ่งที่สร้างออกมาตั้งใจมากขึ้น จังหวะก็สำคัญ — compact ที่จุดเปลี่ยนเฟส หลังแผนลงตัวแล้ว ไม่ใช่กลางงาน เทียบกับ clearing ที่ทิ้งทุกอย่างแล้วเริ่มเย็นชืด compaction พยายามพาสิ่งจำเป็นข้ามไป clearing พนันว่ามันถูกเขียนไว้ที่อื่นที่ดีกว่าอยู่แล้ว

Autocompact

บีบอัตโนมัติ — การบีบบริบทที่ harness สั่งเองเมื่อ context ใกล้เต็ม

ทำไมต้องรู้
มันเกิดโดยเราไม่ได้เลือกจังหวะ — งานสำคัญอย่าปล่อยให้ชนเพดานเอง
อ่านเต็ม

compaction ที่ harness สั่งเองโดยอัตโนมัติเมื่อ context window ใกล้เต็ม harness เฝ้าดูว่า context window เต็มแค่ไหน พอข้ามเกณฑ์ (มักราว 80%) มันหยุด ขอให้โมเดลสรุป session ที่ผ่านมา แล้วตั้งต้น session ใหม่ด้วยสรุปนั้น งานดำเนินต่อเหมือนไม่มีอะไรเกิดขึ้น แต่มีอะไรเกิดขึ้นจริง compaction ตกหล่นโดยธรรมชาติ และ autocompact ตกหล่นในจังหวะที่เราไม่ได้เลือก compact แบบสั่งเองเกิดที่จุดเปลี่ยนเฟส ตอนที่เราบอกโมเดลได้ว่าต้องเก็บอะไรไว้ autocompact ยิงกลางงาน เมื่อไหร่ก็ตามที่ถึงเกณฑ์ — อาจกลางการ refactor พอดี โดยสรุปตัดสินใจเองว่าการตัดสินใจไหนของเราคุ้มค่าจะเก็บไว้ อาการคลาสสิก: agent เดินหน้าต่ออย่างมั่นใจแต่แอบลืมข้อจำกัดที่ตั้งไว้เมื่อชั่วโมงก่อนไปเงียบ ๆ แล้วเราสังเกตได้ก็ตอนที่งานของมันเริ่มขัดแย้งกับข้อจำกัดนั้นแล้ว การป้องกันคือไม่ปล่อยให้มันยิง เฝ้าดูตัวบอก context แล้ว compact เองตอนถึงจุดเปลี่ยนธรรมชาติ หรือเขียนการตัดสินใจลงเอกสารแผนหรือ handoff artifact บนดิสก์ ที่ไม่มีสรุปไหนทำหายได้ harness ส่วนใหญ่ยังให้ปรับ buffer ได้ — เลื่อนเกณฑ์ให้เร็วขึ้นหรือช้าลง หรือปิด autocompact ไปเลย เพื่อปรับว่าจะเหลือที่ว่างไว้แค่ไหนก่อนมันยิง

Section 6

6 · ความจำและการบังคับทิศ

วิธีทำให้ agent รู้สิ่งที่ควรรู้ โดยไม่ยัดทุกอย่างเข้า context

Memory system

ระบบความจำ — ระบบที่พยายามทำให้ agent จำข้ามเซสชันได้ ด้วยการเขียนลงสภาพแวดล้อมแล้วโหลดกลับตอนเริ่ม session

ทำไมต้องรู้
ไม่ใช่ความจำจริงของโมเดล เป็นการเขียน-อ่านไฟล์ ถ้า readback ไม่ผ่าน = ยังไม่ได้จำ
อ่านเต็ม

ระบบที่พยายามทำให้ agent มีสถานะคงอยู่ข้าม session ได้ ด้วยการเขียนข้อมูลลงสภาพแวดล้อมระหว่าง session แล้วโหลดกลับเข้า context window ตอนเริ่ม session ถัดไป ทำให้ agent พาความต่อเนื่องข้ามการ clear ของผู้ใช้ไปได้ memory system มีสองส่วน: เส้นทางเขียน — ระหว่าง session agent บันทึกสิ่งที่เรียนรู้ (ความชอบที่เราบอก ข้อเท็จจริงเกี่ยวกับโปรเจกต์) เป็นไฟล์ในสภาพแวดล้อม เส้นทางอ่าน — ตอนเริ่ม session harness โหลดไฟล์เหล่านั้น หรือดัชนีของมัน กลับเข้า context window harness หลายตัวมี memory system ของตัวเอง (Claude Code มี /memory) แต่เราสร้างเองก็ได้ — โฟลเดอร์โน้ตบวกคำสั่งใน AGENTS.md ให้มันไปอ่าน ข้อแลกเปลี่ยนเดียวกับเนื้อหาที่โหลดตลอดเวลาทุกแบบใช้ได้ที่นี่ ความจำสะสมมากขึ้นเรื่อย ๆ ระบบส่วนใหญ่จึงโหลดแค่ดัชนีบรรทัดเดียว ทิ้งเนื้อหาไว้หลัง context pointer แทนที่จะยัดทุกอย่างเข้าไปเลย และความจำเป็น secondary source มันจึงล้าสมัยได้ — ข้อเท็จจริงที่บันทึกไว้เดือนมีนาคม ถูกโหลดด้วยความมั่นใจเท่ากันในเดือนมิถุนายน หลังโปรเจกต์เดินหน้าไปแล้ว memory system ต้องถูกตัดแต่งเหมือน AGENTS.md เหมือนกัน

AGENTS.md

ไฟล์บรีฟประจำโปรเจกต์ — ไฟล์ในสภาพแวดล้อมที่ harness โหลดเข้า context ตอนเริ่ม session — บรีฟถาวรของโปรเจกต์ถึง agent

ทำไมต้องรู้
ที่ที่ควรเก็บกฎที่ต้องใช้ทุกครั้ง ไม่ใช่พิมพ์ซ้ำทุกเทิร์น
อ่านเต็ม

ไฟล์ในสภาพแวดล้อมที่ harness โหลดเข้า context window ตอนเริ่ม session — บรีฟถาวรของโปรเจกต์ถึง agent เป็นข้อตกลงข้ามหลาย harness บาง harness ก็มีตัวแปรของตัวเอง (Claude Code คือ CLAUDE.md) เพราะมันโหลดอัตโนมัติ นี่คือวิธีหนึ่งที่หลีกเลี่ยงการพูดซ้ำข้ามหลาย session ได้ โมเดลไม่มีสถานะค้าง คำแก้ไขที่ให้ไปใน session หนึ่งหายไปใน session ถัดไป จนเราต้องบอก session ใหม่ทุกครั้งว่าโปรเจกต์ใช้ pnpm เทสรันด้วย flag เฉพาะ ไดเรกทอรีหนึ่งถูก generate ขึ้นมาไม่ควรแตะ พอแก้ไข agent เรื่องเดิมซ้ำสองครั้งแล้ว นั่นคือตัวเลือกที่ควรเอาไปเขียนใน AGENTS.md เนื้อหาที่เหมาะคือสิ่งที่ agent อนุมานจากโค้ดเองไม่ได้: คำสั่ง build และ test ข้อตกลงที่โค้ดเบสไม่ได้ทำให้ชัดเจน ข้อจำกัดตายตัว ("ห้ามแก้ generated client เด็ดขาด") สั้นและชี้ตรง — มันคือบรีฟ ไม่ใช่เอกสารประกอบ ข้อแลกเปลี่ยนคือทุกอย่างในนั้นถูกโหลดตลอดเวลา คำสั่งสะสมมากขึ้น ส่วนใหญ่ไม่เกี่ยวกับงานตรงหน้า AGENTS.md ที่ยาวทั้งเสียโทเคนและเจือจางตัวเอง — ยิ่งมีคำสั่งใน context มากเท่าไหร่ โมเดลยิ่งทำตามแต่ละอันได้ไม่แน่นอนมากขึ้น

Progressive disclosure

เปิดเผยเป็นชั้น — โหลดเฉพาะ context ที่ต้องใช้ตอนนี้ ที่เหลือทิ้งตัวชี้ไว้ ยืมแนวคิดมาจากงานออกแบบ UI

ทำไมต้องรู้
ทางออกจริงของปัญหา context บวม — ไม่ใช่ซื้อ context window ใหญ่ขึ้น
อ่านเต็ม

โหลดเฉพาะ context ที่ agent ต้องใช้ตอนนี้ พร้อม context pointer ไปยังส่วนที่เหลือ ยืมมาจากงานออกแบบ UI ที่หมายถึงการโชว์เฉพาะปุ่มควบคุมที่เกี่ยวกับงานตรงหน้าของผู้ใช้ ซ่อนที่เหลือไว้หลังการคลิก เทคนิคนี้มีอยู่เพราะ context มีต้นทุนสองต่อ ทุกโทเคนที่โหลดไว้ล่วงหน้าถูกคิดเป็น input tokens ทุกเทิร์น และทุกโทเคนก็แย่ง attention budget ไม่ว่า agent จะต้องใช้มันหรือไม่ AGENTS.md ที่ยัดคู่มือสไตล์เต็ม runbook การ deploy และข้อตกลงฐานข้อมูลไว้ ทำให้ agent แย่ลงในทุกเรื่องพร้อมกัน — คำสั่งที่สำคัญกับงานตรงหน้าถูกเจือจางด้วยคำสั่งที่ไม่เกี่ยว จุดสังเกตคือ agent เมินกฎที่เรารู้ว่าอยู่ใน context ของมัน — มันอยู่จริง แต่ถูกฝังไว้ progressive disclosure กลับด้าน: เก็บชั้นที่โหลดตลอดเวลาให้เล็ก — หนึ่งประโยคต่อหัวข้อ บวกตัวชี้ไปที่รายละเอียดอยู่ที่ไหน agent อ่านคู่มือสไตล์ตอนกำลังเขียน component อ่าน runbook การ deploy ตอนกำลัง deploy และไม่อ่านทั้งคู่ตอนกำลังแก้เทส skills คือแพทเทิร์นที่สร้างไว้ใน harness แล้ว: คำอธิบายสั้น ๆ โหลดทุก session คำสั่งเต็มโหลดเฉพาะตอนถูกกระตุ้น

ตัวชี้บริบท — การอ้างถึงเอกสารอื่นในเอกสารหนึ่ง เพื่อให้ agent ดึงเข้ามาเฉพาะตอนที่งานต้องใช้

ทำไมต้องรู้
ทำให้ไฟล์บรีฟสั้นได้โดยไม่เสียความครบ
อ่านเต็ม

การอ้างถึงในเอกสารหนึ่งที่ชี้ไปยังอีกเอกสาร เพื่อให้ agent ดึงมันเข้า context window ได้เฉพาะตอนงานต้องใช้จริง เป็นหน่วยที่ progressive disclosure ถูกสร้างขึ้นจากมัน เหตุผลที่ใช้ตัวชี้ (แทนที่จะฝังเนื้อหาเข้าไปตรง ๆ) คือเรื่องต้นทุน ตัวชี้เดียวกินพื้นที่แค่หนึ่งบรรทัดใน context window เอกสารข้างหลังมันอาจมีเป็นพันโทเคน แต่โทเคนเหล่านั้นไม่มีต้นทุนอะไรจนกว่า agent จะตามตัวชี้ไปจริง ฝัง runbook 2,000 โทเคนไว้ใน AGENTS.md แล้วทุก session ต้องจ่ายค่ามันตลอด แทนที่ด้วย "ขั้นตอน deploy: ดูที่ internal/deploy.md" มีแค่ session ที่ deploy จริงถึงจะโหลดมัน agent ตามตัวชี้ด้วย tool call เมื่องานตรงกัน ตัวชี้ต้องมีสองส่วนถึงจะทำงานได้: path ที่คงที่ กับคำอธิบายมากพอให้ agent รู้ว่าเมื่อไหร่ควรตาม path เปล่า ๆ คือตัวชี้ที่ agent ไม่มีเหตุผลจะตาม "ดูที่ internal/deploy.md" โดยไม่บอกใบ้ว่าข้างในมีอะไร จะถูกข้ามไปโดย session ที่ต้องการมันจริง เขียนให้ตรงกับลักษณะงานที่โผล่มา: "release, deploy หรือ rollback — อ่าน internal/deploy.md ก่อน" ตัวชี้อยู่ทุกที่เมื่อสังเกตดี ๆ: บรรทัดใน AGENTS.md คำอธิบาย skill (harness โหลดคำอธิบาย เนื้อหา skill รอข้างหลัง) ชื่อไฟล์ในรายการไดเรกทอรี ลิงก์ระหว่างเอกสาร ตัวชี้ยังผูก secondary source กลับไปยัง primary source ที่มันมาจากได้ด้วย — สรุป compaction ที่ระบุชื่อ transcript ต้นฉบับ เอกสารที่ระบุชื่อไฟล์ต้นฉบับที่มันบรรยาย ทำให้ความตกหล่นของ secondary source กู้กลับมาได้ เมื่อสรุปไม่พอ agent ตามตัวชี้ไปอ่านต้นฉบับแทนที่จะทำงานจากสิ่งที่สรุปเก็บไว้

Skill

สกิล — ความสามารถที่สอนได้ มัดรวมเป็นก้อน เก็บไว้นอก context จนกว่าตัวชี้บริบทจะดึงเข้ามาใช้

ทำไมต้องรู้
วิธีเพิ่มความสามารถโดยไม่กินที่ใน context ตลอดเวลา
อ่านเต็ม

ความสามารถที่สอนได้ มัดรวมเป็นหน่วยเดียว — คำสั่งและทรัพยากรสำหรับทำงานหนึ่งอย่างให้ดี เก็บไว้ในสภาพแวดล้อมจนกว่า context pointer จะดึงมันเข้า context window สำหรับงานตรงหน้า เป็นหน่วยของ progressive disclosure ใน harness Skills เป็นมาตรฐานเปิด นิยามไว้ที่ agentskills.io — เดิมพัฒนาโดย Anthropic แล้ว harness หลักส่วนใหญ่รับไปใช้ ทำให้ skill ที่เขียนครั้งเดียวใช้ได้ข้าม harness รูปแบบคือโฟลเดอร์ที่มี: ไฟล์ SKILL.md (ข้อมูลกำกับ อย่างน้อยชื่อกับคำอธิบาย บวกคำสั่งจริง) สคริปต์ที่ agent รันได้ (ถ้ามี) เทมเพลตและเอกสารอ้างอิงที่คำสั่งชี้ไป (ถ้ามี) มีแค่ชื่อกับคำอธิบายเท่านั้นที่อยู่ใน context โดยดีฟอลต์ พอ task ของ agent ตรงกัน มันโหลดที่เหลือเข้ามา จนกว่าจะถึงตอนนั้น skill กินพื้นที่แทบไม่มีเลย — แค่หนึ่งหรือสองประโยคของโทเคน ไม่ว่าคำสั่งเต็มจะยาวแค่ไหน สิ่งนี้ทำให้ skill ต่างจาก AGENTS.md ที่โหลดเข้าทุก session ไม่ว่างานจะเกี่ยวหรือไม่ skill ถูกอ่านเมื่อมีงานแบบนั้นโผล่มา (release, สร้าง service ใหม่, เขียน migration) และถูกละไว้ในเวลาอื่น

Subagent

เอเจนต์ลูก — agent ที่ถูก agent อื่นสร้างผ่าน tool call รันใน session ของตัวเอง คืนผลกลับมาเป็น tool result ก้อนเดียว และแตกลูกต่อไม่ได้

ทำไมต้องรู้
ใช้กันงานค้นหาที่รกไม่ให้มาเปลือง context ของตัวหลัก
อ่านเต็ม

agent ที่ถูก agent อื่นสร้างขึ้นผ่าน tool call รันใน session ของตัวเอง มี context window ของตัวเอง แล้วรายงานกลับเป็น tool result ก้อนเดียว ต่างจาก handoff (ผู้ให้กำเนิดคาดหวังผลตอบกลับจริง ๆ ส่วน handoff ไม่มีทางกลับ) แตกลูกต่อไม่ได้ — ต้นไม้ลึกแค่ชั้นเดียว subagent มีไว้แยก context ออกไป ไม่ใช่สร้างลำดับชั้นซ้อนกัน จุดประสงค์คือกันงานที่รกออกจาก context ของตัวหลัก การค้นหากว้าง ๆ หรือการอ่านไฟล์ยาวนานสร้าง tool result หลายหน้า ซึ่งส่วนใหญ่สำคัญแค่ตอนหาคำตอบเจอ รันในตัวหลักแล้วทั้งหมดนี้ค้างอยู่ใน context ของตัวหลักไปตลอด session รันใน subagent แทน noise จะเติมเต็ม window ที่ใช้แล้วทิ้งแทน มีแค่รายงานสุดท้ายเท่านั้นที่ลงไปใน context ของตัวหลัก รายงานเป็น secondary source — ตัวหลักได้คำบอกเล่าของ subagent ว่าเจออะไร ไม่ใช่ผลลัพธ์ดิบ อะไรที่รายงานตกหล่นก็มองไม่เห็นสำหรับตัวหลัก subagent ยังรันพร้อมกันได้ด้วย — ตัวหลักแตกงานหลายชิ้นออกไปพร้อมกันได้ในงานที่เป็นอิสระต่อกัน

7 · รูปแบบการทำงาน

เลือกโหมดการทำงานให้ตรงกับความเสี่ยงของงาน

Human-in-the-loop

มีคนอยู่ในลูป — รูปแบบที่มนุษย์ทำงานคู่กับ agent ระหว่าง session — คอยตรวจ เปลี่ยนทิศ หรือช่วยคิดแบบเรียลไทม์

ทำไมต้องรู้
โหมดที่เหมาะกับงานที่ผิดแล้วแก้ยาก
อ่านเต็ม

รูปแบบการทำงานที่มนุษย์หนึ่งคนหรือมากกว่าทำงานคู่กับ agent ระหว่าง session — รีวิว บังคับทิศ หรือร่วมมือแบบเรียลไทม์ มนุษย์อยู่ตรงนั้นและมีส่วนร่วมจริง ไม่ใช่แค่คอยอนุมัติแต่ละการกระทำเฉย ๆ สิ่งที่ตรงข้ามคืองานแบบ AFK ที่ agent รันไม่มีคนเฝ้าแล้วเราตัดสินผลลัพธ์ทีหลัง human-in-the-loop คือการจับปัญหาตอนที่มันยังถูกแก้ได้ถูก — เราเห็น agent เอื้อมไปหยิบไฟล์ผิด อ่านความต้องการผิด หรือเริ่มเดินเข้าทางตัน แล้วบังคับทิศมันด้วยประโยคเดียว แทนที่จะค้นพบทีหลังว่ามันทำงานมั่นใจไปยี่สิบนาทีบนความผิดพลาดนั้น agent ไม่รู้ตัวเองแน่ชัดเวลาหลุดทาง ปล่อยไว้เฉย ๆ มันมักดันไปข้างหน้าต่อมากกว่าจะหยุดถาม รูปแบบไหนเหมาะกับงานไหนขึ้นกับตัวงาน งานที่ระบุชัดเจน เสี่ยงต่ำ ตรวจสอบง่าย เหมาะกับ AFK งานที่คลุมเครือ ย้อนกลับไม่ได้ หรือตรวจผลลัพธ์สุดท้ายยาก (migration schema การตัดสินใจออกแบบยาก อะไรก็ตามที่แตะ production) เหมาะกับการอยู่ในลูป การตัดสินใจโดยพื้นฐานคือ: ทางเดินผิดหนึ่งครั้งแพงแค่ไหน และเราจะจับได้ช้าแค่ไหนถ้าไม่อยู่ในลูป งานบางอย่างเป็น in-the-loop โดยธรรมชาติ เพราะปฏิกิริยาของเราคืออินพุตเอง grilling ใช้ได้ก็ต่อเมื่อเราอยู่ตอบคำถาม prototyping ใช้ได้ก็ต่อเมื่อเราอยู่ตอบสนองต่อชิ้นงาน การอยู่ในลูปมีต้นทุนคือความสนใจของเรา ซึ่งเป็นทรัพยากรหายาก ส่วนหนึ่งของการเก่งขึ้นกับ agent คือการย้ายงานออกจากลูปได้อย่างปลอดภัยมากขึ้น — ด้วยแผน automated check และ human review ตอนท้ายแทนที่จะเฝ้าตลอด

AFK

ปล่อยรันไม่นั่งเฝ้า — เริ่มงานแล้วเดินออกไป ปล่อย agent รันเอง

ทำไมต้องรู้
ความคลุมเครือที่เราไม่ได้เคลียร์ตอนต้น จะถูกมันเดาแล้วต่อยอดผิดไปทั้งกอง
อ่านเต็ม

ปล่อยรันไม่นั่งเฝ้า (away from keyboard) รูปแบบการทำงานที่ผู้ใช้เริ่ม session แล้วปล่อย agent รันโดยไม่มีคนเฝ้า เป็นตัวคูณผลผลิตของงานเขียนโค้ดด้วย AI — หลาย session แบบ AFK รันขนานกันได้ระหว่างที่เรานอน กิน หรือทำงานอื่น ปกติต้องมี permission mode ที่หลวมพอบวก sandbox ถึงจะปลอดภัย ตอนที่เราไม่อยู่ agent จัดการความคลุมเครือต่างไป ตอนเรากำลังเฝ้าดู การตัดสินใจที่คลุมเครือจะโผล่มาเป็นคำถามแล้วเราตอบ พอเราเดินออกไปแล้ว agent เลือกค่าดีฟอลต์เองแล้วเดินหน้าต่อ ทุกการตัดสินใจถัดไปต่อยอดจากการเดานั้น ความล้มเหลวที่เป็นเอกลักษณ์คือกลับมาเจองานหลายชั่วโมงที่เสร็จแล้วมั่นใจ สร้างบนการตัดสินใจผิดที่เกิดขึ้นในสิบนาทีแรก งานไม่ได้สะเพร่า มันสอดคล้องกันดี แค่สอดคล้องกันกับสิ่งที่ผิด เพราะให้ input ระหว่างรันไม่ได้ ให้มันก่อนกับหลังแทน ก่อน: เคลียร์ความคลุมเครือล่วงหน้า — session แบบ grilling, spec ที่เขียนไว้ — เพื่อให้ agent ต้องเติมช่องว่างเองน้อยลง ระหว่าง: automated check กับ automated review ทำหน้าที่แทนความสนใจที่เราไม่ได้ให้ จับสิ่งที่จับได้เชิงกลไกให้เร็ว หลัง: จบงานด้วยอะไรที่รีวิวได้ — เป็น PR ไม่ใช่การเปลี่ยนแปลงที่ merge ไปแล้ว AFK ไม่ได้ตัด human review ออก มันแค่เลื่อนทั้งหมดไปไว้ท้ายสุด ซึ่งเป็นเหตุผลที่สิ่งที่มาถึงตอนท้ายต้องคุ้มค่าที่จะรีวิว นี่ก็เป็นเหตุผลที่ AX สำคัญที่สุดในงาน AFK — ไม่มีใครเฝ้า สภาพแวดล้อมคือความช่วยเหลือเดียวที่ agent มี

Automated check

ตัวตรวจอัตโนมัติ — การตรวจแบบผลลัพธ์แน่นอนที่รันในสภาพแวดล้อม — test, type check, lint, build, pre-commit ผ่านหรือไม่ผ่าน ไม่มีการตีความ

ทำไมต้องรู้
เป็นตาแทนเราตอนไม่ได้เฝ้า และเถียงไม่ได้
อ่านเต็ม

การตรวจสอบแบบผลลัพธ์แน่นอนที่รันในสภาพแวดล้อม — เทส type check lint build pre-commit hook ผ่านหรือไม่ผ่าน ไม่มีการตีความ เป็นสัญญาณที่ agent แก้ไขตัวเองได้โดยไม่ต้องมีใครเข้ามาเกี่ยว เทสที่ flaky คือ check ที่พัง ไม่ใช่ non-check — automated check ต้อง deterministic โดยการออกแบบ การแก้ไขตัวเองทำงานเป็นลูป: agent แก้ไข รัน check เป็น tool call ผลลัพธ์ error ลงไปใน context window — type error พร้อมไฟล์และบรรทัด assertion ที่ล้มเหลวพร้อมค่าที่คาดหวังกับค่าจริง แค่นี้พอให้ agent แก้ปัญหาแล้วรัน check ใหม่ วนไปเรื่อย ๆ จนผ่าน โดยไม่มีมนุษย์ในลูปเลย ความแน่นอนคือสิ่งที่ทำให้ลูปนี้เชื่อถือได้ โค้ดเดียวกันให้ผลตัดสินเดียวกันเสมอ ผ่านจึงมีความหมายจริง check ที่ flaky ทำลายสิ่งนี้ — agent "แก้" โค้ดที่ดีอยู่แล้ว หรือ retry ผ่านความล้มเหลวจริง ๆ ไปเฉย ๆ นี่คือเหตุผลที่ check ดี ๆ เป็นส่วนใหญ่ของ AX ของโค้ดเบส agent ใน repo ที่มี type เข้มงวด test suite เร็ว และ linter จับความผิดพลาดของตัวเองได้ส่วนใหญ่ก่อนที่เราจะเห็น agent ใน repo ที่ไม่มีสิ่งเหล่านี้เลยจะส่งของอะไรก็ตามที่มันผลิตออกมา ความต่างนี้สำคัญที่สุดในงาน AFK ที่ check เป็นการตรวจสอบเดียวที่เกิดขึ้นระหว่างรัน แต่ check จับได้แค่สิ่งที่มัน assert ไว้เท่านั้น — check ผ่านหมายถึงคุณสมบัติที่ assert ไว้ถูกต้อง ไม่ได้แปลว่าโค้ดถูกต้องทั้งหมด ช่องว่างที่ต้องใช้วิจารณญาณเป็นหน้าที่ของ automated review กับ human review

จับปัญหาที่ test จับไม่ได้ แต่อย่าใช้แทนการตรวจของมนุษย์
อ่านเต็ม

agent หนึ่งรีวิวงานของอีก agent มักใช้โมเดลหรือ system prompt คนละตัว ไม่ deterministic เพราะมันสร้างการตัดสินใจ รันได้ทุกที่ — ก่อน merge บน PR หลังเกิดเหตุบน commit history กลาง session แบบ subagent LLM-as-judge ใน CI คือ automated review ไม่ใช่ automated check — สิ่งที่ assertion ทำต่างหากที่ตัดสินหมวดหมู่ ไม่ใช่ว่ารันที่ไหน การแยกจาก agent ที่ทำงานคือสิ่งที่ทำให้มันได้ผล ให้ agent ที่เขียนโค้ดรีวิวงานของตัวเองได้น้อยมาก — session ที่สร้างบั๊กก็มีเหตุผลที่สร้างบั๊กนั้นอยู่ในตัวมันด้วย agent อ่านข้อสรุปของตัวเองแล้วยืนยันมันเป็นการรับรอง reviewer ที่มี context window สดใหม่ไม่มีความผูกพันนั้นเลย มันเห็น diff แบบที่คนแปลกหน้าเห็น ซึ่งเป็นสิ่งที่การรีวิวต้องพึ่งพา โมเดลคนละตัวหรือ system prompt เฉพาะทางรีวิวยิ่งช่วยเสริม — จุดบอดต่างกัน และ system prompt ที่โฟกัสสิ่งที่เราสนใจจริง (ความปลอดภัย สัญญา API ประสิทธิภาพ) ดีกว่า "หาปัญหาทั่วไป" มันแทรกอยู่ระหว่างชั้นการรีวิวอื่น automated check เป็น deterministic จับสิ่งที่ assert ได้เชิงกลไก human review แพงและขยายผลได้แย่ที่สุด automated review อยู่ตรงกลาง จับปัญหาที่ต้องใช้วิจารณญาณ (ชื่อฟังก์ชันที่ทำให้เข้าใจผิด edge case ที่พลาด) ด้วยต้นทุนระดับเครื่องจักร เพราะไม่ deterministic มันพลาดได้และ flag เรื่องที่ไม่ใช่ปัญหาได้ ให้มองมันเป็นตัวกรองที่ยกพื้นก่อนคนดู ไม่ใช่ประตูที่แทนที่คนไปเลย

Human review

รีวิวโดยมนุษย์ — ผู้ใช้อ่านโค้ดที่ agent เขียนแล้วตัดสินเอง — อ่าน diff ถึงนับ อ่านแต่บทสรุปไม่นับ

ทำไมต้องรู้
เส้นแบ่งจริงระหว่างงานที่ตรวจแล้วกับงานที่แค่ดูสวย
อ่านเต็ม

ผู้ใช้อ่านโค้ดที่ agent ผลิตแล้วตัดสินเอง อ่าน diff หรือไฟล์ที่เปลี่ยนนับ อ่านคำบรรยายของ agent ว่าทำอะไรไม่นับ — การเล่าไม่ใช่ตัวชิ้นงาน คำบรรยายเป็น secondary source เขียนโดยฝ่ายที่ถูกรีวิวเอง diff คือ primary source และการรีวิวหมายถึงอ่านมันจริง agent ทำให้ปริมาณโค้ดที่ผลิตออกมาเพิ่มขึ้น การรีวิวจึงกลายเป็นคอขวด แนวคิดที่มีประโยชน์คือจัดชั้นกลยุทธ์การรีวิวต่างกัน automated check จับความล้มเหลวเชิงกลไก automated review จับสิ่งที่บรรยายได้ human review เก็บไว้สำหรับสิ่งที่มีแต่เราเท่านั้นตัดสินได้ — การเปลี่ยนแปลงนี้ถูกต้องไหม แนวทางนี้เข้ากับโค้ดเบสไหม สิ่งนี้ควรมีอยู่หรือเปล่า การรีวิวยังถูกกว่าถ้าทำเร็ว อ่านแผนก่อนเริ่มงาน หรือ diff เล็ก ๆ ระหว่างทาง ใช้เวลาไม่กี่นาที ขุดสาขาที่เสร็จแล้วหลังงาน AFK ใช้เวลานานกว่า จุดที่วางเช็คพอยต์การรีวิวเป็นการตัดสินใจแบบ human-in-the-loop ไม่ใช่เรื่องคิดทีหลัง

Vibe coding

โค้ดตามความรู้สึก — รับโค้ดที่ agent เขียนโดยไม่อ่าน มอง diff เป็นกล่องทึบ

ทำไมต้องรู้
เร็วมากสำหรับของทิ้งขว้าง และอันตรายมากสำหรับของที่ต้องดูแลต่อ
อ่านเต็ม

รูปแบบการทำงานที่ผู้ใช้รับโค้ดของ agent โดยไม่ทำ human review diff ถูกมองเป็นกล่องทึบ — สิ่งที่สำคัญคือโปรแกรมทำงานถูกไหม ไม่ใช่ข้างในมีอะไร automated review กับ automated check อาจยังรันอยู่ก็ได้ vibe coding ไม่พูดถึงทั้งสองอย่าง คำนี้มาจาก Andrej Karpathy ที่บัญญัติต้นปี 2025 — "ยอมจำนนกับความรู้สึกเต็มที่" และ "ลืมไปเลยว่าโค้ดมีอยู่จริง" บรรยายสิ่งที่ต้องการ รับสิ่งที่ได้กลับมา ตัดสินด้วยการรันดู vibe coding แลกการตรวจสอบกับความเร็ว การอ่าน diff มักเป็นขั้นตอนที่ช้าที่สุดในงานที่ขับเคลื่อนด้วย agent ตัดมันออกก็ตัดคอขวดหลักออกไปด้วย สำหรับโค้ดที่ความล้มเหลวราคาถูก — prototype สคริปต์ใช้ครั้งเดียว เครื่องมือภายใน — นี่คือการแลกที่สมเหตุสมผล ความเสี่ยงแปรตามอายุขัยและเดิมพันของโค้ดนั้น ต้นทุนมาทีหลัง งานที่ vibe coding สะสมกลายเป็นโค้ดเบสที่ไม่มีใครอ่านเลย และมีแค่พฤติกรรมเท่านั้นที่ถูกเช็ค ฉะนั้นอะไรที่พฤติกรรมไม่โผล่ให้เห็น เช่น ความลับที่หลุดลง log, edge case ที่ขาด, การจัดการข้อมูลผิดแบบเงียบ ๆ จะหลุดออกไปโดยไม่มีใครเห็น ครั้งแรกที่ใครสักคนดีบักระบบคือครั้งแรกที่มีใครอ่านโค้ดจริง ๆ พอ human review หายไป การตรวจสอบอัตโนมัติที่ยังรันอยู่ (เทส type automated review) คือประตูเดียวที่โค้ดต้องผ่าน

Design concept

ภาพร่วมของสิ่งที่จะสร้าง — ความเข้าใจร่วมกันว่ากำลังสร้างอะไร ถือร่วมกันระหว่างคนกับ agent แต่แยกจากตัวชิ้นงาน

ทำไมต้องรู้
ถ้าภาพนี้ไม่ตรงกัน โค้ดจะสวยแต่ผิดเรื่อง
อ่านเต็ม

ความเข้าใจร่วมกันว่ากำลังสร้างอะไร ถือร่วมกันระหว่างผู้ใช้กับ agent แต่แยกจากตัวชิ้นงานใด ๆ คำนี้มาจาก Brooks (The Design of Design): บทสนทนา handoff artifact และโค้ด ล้วนเป็นทรัพย์สินที่พยายามจับหรือเข้าถึง design concept แต่ไม่มีอันไหนเป็นตัวมันเอง คุณภาพของ design concept รู้สึกได้ผ่านคุณภาพของบทสนทนาที่สร้างมันขึ้นมา คำนี้ตั้งชื่อช่องว่างเบื้องหลังความหงุดหงิดที่คุ้นเคย: agent เขียนตรงตามที่เราขอเป๊ะแล้วมันยังผิดอยู่ดี สาเหตุปกติคือเรายังคิดไม่จบว่าต้องการอะไรจริง ๆ design concept ยังไม่เสร็จในหัวเราเอง prompt ของเราจับได้แค่ส่วนที่เราคิดออกแล้ว และเงียบในส่วนที่ยังคิดไม่ออก agent เติมความเงียบนั้นด้วยสมมติฐานของตัวเอง เพราะไม่มีอะไรให้จัดแนวด้วย ไม่มีอะไรทำงานผิดพลาด แค่ยังไม่มี design concept ร่วมกัน เพราะยังไม่มีของทั้งก้อนให้แบ่งปัน เรารู้ว่า design concept ถูกแชร์แล้วเหมือนกับที่รู้กับเพื่อนร่วมงาน — อีกฝ่ายเริ่มตอบคำถามที่เรายังไม่ได้ถามแบบเดียวกับที่เราจะตอบ จนกว่าจะถึงจุดนั้น งานคือบทสนทนา — grilling คือเวอร์ชันที่จงใจทำ และการเขียน spec เร็วเกินไปก็แค่จับความไม่ลงรอยไว้ในทรัพย์สินที่คงทนกว่าเดิม design concept ยังขยับตามที่เราเรียนรู้ ทรัพย์สินตามหลังมันเสมอ นี่คือเหตุผลที่ spec ซึ่งซื่อสัตย์ต่อความเข้าใจของสัปดาห์ก่อนยังชี้นำผิดให้ session ของสัปดาห์นี้ได้

Grilling

การซักไล่ — เทคนิคสร้างภาพร่วม โดยให้ agent สัมภาษณ์ผู้ใช้แบบซักทีละการตัดสินใจ

ทำไมต้องรู้
ดันความคลุมเครือขึ้นมาก่อนลงมือ ถูกกว่าค้นเจอทีหลังมาก
อ่านเต็ม

เทคนิคพัฒนา design concept กับ agent: agent สัมภาษณ์ผู้ใช้แบบโสกราตีส ทีละการตัดสินใจ เสนอคำตอบแนะนำสำหรับแต่ละข้อ ชะลอความรีบร้อนที่จะได้แผนที่เสร็จสมบูรณ์ — ไม่มี handoff artifact ไหนถูกเขียนจนกว่า concept จะนิ่ง เทคนิคนี้มีอยู่เพราะ agent เติมช่องว่างแบบเงียบ ๆ ถ้าขอให้เขียน spec จาก prompt สองบรรทัด agent จะไม่หยุดที่การตัดสินใจที่เรายังไม่ได้ทำ มันเลือกค่าดีฟอลต์แล้วเขียนลงไปเลย ผลลัพธ์ดูสมบูรณ์ และการเดากับตัวเลือกจริงแยกไม่ออก เราจึงค้นพบมันช้า — ตอนรีวิว หรือตอนฟีเจอร์ที่สร้างเสร็จจัดการ edge case แบบที่เราไม่เคยเลือก grilling กลับด้าน — แทนที่จะเดา agent ต้องถาม เป็นเทคนิคแบบ human-in-the-loop คำตอบของเราคืออินพุต เมื่อคำถามตอบในบทสนทนาไม่ได้ (ต้องเห็นของจริงถึงจะตอบได้) ให้เปลี่ยนไปใช้ prototyping แทน

Prototyping

ทำตัวอย่างหยาบ — ให้ agent สร้างของหยาบ ๆ เร็ว ๆ เมื่อคุยกันอย่างเดียวแล้วยังเห็นไม่ตรงกัน

ทำไมต้องรู้
ของจริงชิ้นเล็กสื่อสารได้ชัดกว่าคำอธิบายยาว ๆ
อ่านเต็ม

ให้ agent สร้างเวอร์ชันหยาบ ๆ อย่างเร็ว สำหรับตอนที่บทสนทนามีความละเอียดต่ำเกินไปและต้องมีชิ้นงานจริงมาคุยกัน grilling แก้การตัดสินใจเชิงออกแบบในบทสนทนา บทสนทนาถูกแต่ความละเอียดต่ำ — บางคำถามตอบเป็นคำพูดไม่ได้ เช่นการมีปฏิสัมพันธ์รู้สึกยังไง API มีรูปร่างที่ใช้งานสะดวกในโค้ดจริงไหม เลย์เอาต์ทำงานได้กับข้อมูลขนาดจริงไหม พอสัมภาษณ์ไปเจอคำถามแบบนี้ คำตอบที่ซื่อสัตย์คือ "ไม่รู้ ต้องเห็นของก่อน" เลยจุดนั้นการถกจะวนไปวนมา แทนที่จะเถียงต่อ ให้ agent สร้างของขึ้นมา ดูมัน แล้วกลับมาคุยต่อพร้อมคำตอบ agent ลดต้นทุนการสร้างของ ทำให้แนวทางนี้ใช้ได้จริง เวอร์ชันหยาบที่เคยใช้เวลาทำโมเดลจำลองหนึ่งวัน ตอนนี้ใช้แค่ไม่กี่นาที คุ้มค่าที่จะทำเป็นประจำ เป็นเทคนิคแบบ human-in-the-loop — prototype มีไว้ให้เราตอบสนอง ปกติไม่หยุดแค่ดูครั้งเดียว วนซ้ำกับ prototype — ตอบสนอง ขอให้เปลี่ยน ตอบสนองอีกครั้ง แต่ละรอบแก้การตัดสินใจอีกข้อเทียบกับชิ้นงานจริง ที่ความละเอียดสูงกว่าที่บทสนทนาทำได้ prototype ไม่จำเป็นต้องหยาบทั้งหมด สร้างส่วนที่กำลังประเมินจริงให้ถึงคุณภาพ production ได้เลย พอการตัดสินใจลงตัว component หรือ API ที่เราตอบสนองไปสามารถย้ายเข้าโค้ดเบสจริงได้ ทำให้ prototyping เป็นวัตถุดิบสำคัญที่ spec อ้างอิงได้

DX

ประสบการณ์นักพัฒนา — โค้ดเบสและเครื่องมือทำให้มนุษย์ทำงานดีได้ง่ายแค่ไหน — เอกสาร ความเร็วของ feedback ข้อความ error

ทำไมต้องรู้
ของเดิมที่เราคุ้นอยู่แล้ว ใช้เป็นฐานเทียบกับ AX
อ่านเต็ม

ประสบการณ์นักพัฒนา — โค้ดเบสและ toolchain ของมันทำให้มนุษย์ทำงานดีได้ง่ายแค่ไหน DX ที่ดีคือ feedback ที่เร็ว ข้อความ error ที่ชัดเจน เอกสารที่ตอบคำถามที่เรามีจริง และการตั้งค่าที่ใช้ได้ตั้งแต่ครั้งแรก คำนี้มีมาก่อนงานเขียนโค้ดด้วย AI นานแล้ว อยู่ในพจนานุกรมนี้หลัก ๆ เพื่อเทียบกับ AX DX คือปฏิสัมพันธ์ระหว่างมนุษย์กับโค้ดเบสเท่านั้น ความต่างหลักระหว่างสองกลุ่มผู้ฟังคือมนุษย์มีสถานะคงอยู่ (stateful) ส่วน agent ไม่มี (stateless) มนุษย์เรียนรู้โค้ดเบสครั้งเดียวแล้วพกความรู้นั้นไปทุกวันหลังจากนั้น นี่คือเหตุผลที่ DX แย่ยังอยู่รอดได้ — เลี่ยง CI ช้าด้วยการรวมการ push เลี่ยงเอกสารขาดด้วยการถามใน Slack ครั้งเดียว เลี่ยงโครงสร้างที่งงด้วยการจำเอาว่าอะไรอยู่ที่ไหน วิธีแก้ปัญหาสะสมไปเรื่อย ๆ จนทีมงานได้ผลดีในโค้ดเบสที่ต่อต้านพวกเขาอยู่ agent เจอโค้ดเบสเดียวกันโดยไม่มีการสะสมนั้นเลย ไม่มีสถานะข้าม session มันเรียนรู้โค้ดเบสใหม่ตั้งแต่ศูนย์ทุกครั้ง — มันได้ประโยชน์จาก test suite ที่เร็วและข้อความ error ที่ชัดเจน แต่อะไรที่มันคิดออกเมื่อวานหายไป เว้นแต่จะถูกเขียนลงสภาพแวดล้อม ซึ่ง agent รับรู้ได้แค่ผ่าน tool result เท่านั้น นั่นคือช่องว่างที่ AX ตั้งชื่อ: ส่วนของ DX ที่รอดเมื่อนักพัฒนาเป็น agent บวกเรื่องที่มนุษย์ไม่มี เช่นการรักษา context window ให้ว่าง

ประสบการณ์เอเจนต์ — สภาพแวดล้อมถูกจัดไว้ดีแค่ไหนให้ agent ทำงานดีในโค้ดเบสได้ คู่กับ DX ที่เน้นมนุษย์ พอ agent ตัวเดียวกันทำงานดีใน repo หนึ่งแต่แย่ใน repo อื่น (โมเดลเดียวกัน harness เดียวกัน) ความต่างมักอยู่ที่ AX สัญชาตญาณคือโทษโมเดลหรือเขียน prompt ใหม่ แต่ทางแก้มักอยู่ใน repo มากกว่า AX ที่ดีมีสามมิติหลัก: automated check (เร็ว deterministic เช่น type test lint ที่ agent แก้ไขตัวเองได้โดยไม่ต้องมีมนุษย์), architecture (โค้ดเบสที่ agent เดินเรื่องได้โดยไม่ต้องอ่านทุกอย่าง โครงสร้างคาดเดาได้ พฤติกรรมมากมายซ่อนหลัง interface เล็ก ๆ ชื่อบอกว่าทำอะไร), free context (AGENTS.md, skills และ tools ถูกเก็บให้กระชับ เพื่อให้ context window ส่วนใหญ่ว่างสำหรับงาน agent อยู่ใน smart zone แทนที่จะจมอยู่ใน context ที่ท่วมท้น) AX กับ DX ทับซ้อนกัน — check ที่ดีและสถาปัตยกรรมสะอาดช่วยทั้งสองกลุ่ม แต่ก็แยกออกจากกันได้เหมือนกัน มนุษย์ทนกับความรู้แบบปากต่อปาก CI ที่ช้า และ "ไปถามสาระเรื่อง billing module" ได้ agent ทำไม่ได้ agent ไม่ได้ประโยชน์จาก tooltip ใน IDE หรือ dashboard สวย ๆ พวกมันต้องการความล้มเหลวเป็นข้อความใน tool result โค้ดเบสหนึ่งอาจมี DX ดีแต่ AX แย่ก็ได้
