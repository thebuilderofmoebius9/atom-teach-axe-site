Section 1

1 · ตัวโมเดล

เริ่มจากของจริงที่อยู่ล่างสุด: โมเดลคืออะไร ทำอะไรได้จริง และค่าใช้จ่ายเกิดตรงไหน

AI

ปัญญาประดิษฐ์ — ป้ายชื่อที่ขยับไปเรื่อย ๆ ไม่ใช่เทคโนโลยีตัวใดตัวหนึ่ง ตอนนี้ชี้ไปที่ large language model

ทำไมต้องรู้
เวลาใครพูดว่า AI ให้ถามต่อว่าหมายถึงโมเดลตัวไหน เพราะคำนี้เปลี่ยนความหมายทุก 2-3 ปี

Model

โมเดล — ก้อนตัวเลขที่ทำได้อย่างเดียวคือทายคำถัดไป ไม่มีความจำ ไม่ทำอะไรเองได้

ทำไมต้องรู้
คนมักโทษ 'โมเดลโง่' ทั้งที่ปัญหาส่วนใหญ่อยู่ที่ harness และ context รอบตัวมัน

Parameters

พารามิเตอร์ / weights — ตัวเลขหลักพันล้านข้างในโมเดล ปรับตอนเทรน ทุกอย่างที่โมเดลรู้อยู่ในนี้

ทำไมต้องรู้
อธิบายว่าทำไมโมเดลถึงรู้บางเรื่องโดยไม่ต้องบอก และทำไมสอนเพิ่มระหว่างใช้งานไม่ได้

Training

การเทรน — กระบวนการป้อนข้อความมหาศาลเพื่อปรับพารามิเตอร์ให้ทายคำถัดไปแม่นขึ้น

ทำไมต้องรู้
จบเมื่อไหร่ ความรู้ก็แช่แข็งเมื่อนั้น ต่อจากนั้นต้องป้อนผ่าน context อย่างเดียว

Inference

การรันโมเดล — การเอาโมเดลที่เทรนแล้วมาสร้างคำตอบ พารามิเตอร์ไม่ขยับเลย

ทำไมต้องรู้
ทุกครั้งที่คุยคือ inference — โมเดลไม่ได้ 'เรียนรู้' จากที่คุยกับเรา

Effort

ระดับการคิด — ปุ่มปรับว่าให้โมเดลคิดมากแค่ไหนก่อนตอบ คิดมาก = เปลืองโทเคนขาออกมากขึ้น

ทำไมต้องรู้
งานง่ายเปิด effort สูงคือเผาเงินเปล่า งานยากเปิดต่ำคือได้คำตอบมั่ว

Token

โทเคน — หน่วยเล็กสุดที่โมเดลอ่านและเขียน ประมาณขนาดคำแต่ไม่เท่ากันเป๊ะ

ทำไมต้องรู้
ทั้งขนาด context ราคา และความช้า วัดกันด้วยโทเคนทั้งหมด

Next-token prediction

การทายคำถัดไป — สุ่มคำถัดไปจาก context ต่อท้าย แล้วรันใหม่ วนแบบนี้ไปเรื่อย ๆ

ทำไมต้องรู้
รู้กลไกนี้แล้วจะเข้าใจว่าทำไมโมเดลถึงมั่นใจแม้ตอนที่มันผิด

Non-determinism

ผลลัพธ์ไม่คงที่ — อินพุตเดิมอาจได้เอาต์พุตต่างกัน เป็นธรรมชาติของทั้งการสุ่มคำและฝั่งผู้ให้บริการ

ทำไมต้องรู้
รันสองรอบได้ผลต่างกันเป็นเรื่องปกติ อย่าไปสรุปว่าแก้แล้วหายทั้งที่แค่บังเอิญ

Model provider

ผู้ให้บริการโมเดล — คนที่รันโมเดลให้เรา ปกติอยู่ไกล (Anthropic, OpenAI, Google) หรือรันเองในเครื่องก็ได้ (Ollama)

ทำไมต้องรู้
ปัญหาช้า/ล่ม/quota ส่วนใหญ่อยู่ชั้นนี้ ไม่ใช่ที่โค้ดเรา

Harness

ตัวครอบโมเดล — ทุกอย่างรอบโมเดลที่ทำให้มันกลายเป็น agent — tools, system prompt, การจัดการ context, permission, hook

ทำไมต้องรู้
อัปเกรด harness มักได้ผลมากกว่าเปลี่ยนโมเดล

Model provider request

หนึ่งรอบเรียกโมเดล — หนึ่งรอบไป-กลับระหว่าง harness กับผู้ให้บริการ ส่ง context ไป ได้คำตอบกลับหนึ่งชุด

ทำไมต้องรู้
หน่วยนับเงินและนับเวลาจริงอยู่ตรงนี้ ไม่ใช่ 'ต่อข้อความ'

Input tokens

โทเคนขาเข้า — โทเคนที่ harness ส่งไปทุกรอบ คิดเงินถูกกว่าขาออก

ทำไมต้องรู้
context บวมทุกเทิร์น ค่าใช้จ่ายจึงโตแบบสะสม ไม่ใช่คงที่

Output tokens

โทเคนขาออก — โทเคนที่โมเดลเขียนกลับมา คิดเงินแพงกว่าเพราะใช้การคำนวณมากกว่า

ทำไมต้องรู้
ให้ตอบยาวโดยไม่จำเป็นคือจุดที่บิลพุ่งเร็วที่สุด

Prefix cache

แคชส่วนหัว — ที่เก็บฝั่งผู้ให้บริการ ทำให้รอบถัดไปไม่ต้องประมวลผลส่วนต้นที่เหมือนเดิมซ้ำ

ทำไมต้องรู้
ทำไมการสลับ system prompt ไปมาถึงแพงกว่าที่คิด — มันทำแคชแตก

Cache tokens

โทเคนจากแคช — โทเคนขาเข้าที่ผู้ให้บริการเคยประมวลผลไว้แล้ว คิดเงินถูกกว่ามาก

ทำไมต้องรู้
อ่านบิลแล้วเห็นตัวเลขนี้เยอะ = ระบบใช้แคชได้ดี ไม่ใช่ใช้เยอะเกิน

Section 2

2 · Session, Context Window และ Turn

โมเดลไม่มีความจำ ทุกอย่างที่มันรู้ในวินาทีนั้นอยู่ในกรอบเดียวชื่อ context window

Stateless

ไม่จำอะไรเลย — ไม่พาข้อมูลข้ามรอบ โมเดลเป็นแบบนี้ระหว่างรอบเรียก และ agent เป็นแบบนี้ระหว่าง session โดยดีฟอลต์

ทำไมต้องรู้
ความรู้สึกว่า 'มันจำได้' มาจาก harness ส่งประวัติไปให้ใหม่ทุกรอบ ไม่ใช่ความจำจริง

Context

บริบท — ข้อมูลที่เกี่ยวข้องกับงานตรงหน้า ที่ agent เข้าถึงได้ ณ ตอนนี้

ทำไมต้องรู้
งานพังส่วนใหญ่ไม่ได้พังที่โมเดล แต่พังที่ context ไม่ครบหรือรกเกิน

Context window

กรอบบริบท — ทุกอย่างที่โมเดลเห็นในหนึ่งรอบเรียก มีขนาดจำกัดและต่างกันตามโมเดล

ทำไมต้องรู้
นี่คือช่องเดียวที่โมเดลใช้รับรู้โลก อะไรไม่อยู่ในนี้ = ไม่มีอยู่จริงสำหรับมัน

Stateful

พาข้อมูลต่อได้ — จำข้อมูลข้ามรอบได้ session เป็นแบบนี้ข้ามเทิร์น ส่วน agent ต้องมี memory system ถึงจะข้าม session ได้

ทำไมต้องรู้
แยกให้ออกว่าอะไร 'จำได้จริง' กับอะไร 'ถูกโหลดกลับมาใหม่'

Agent

เอเจนต์ — โมเดลที่ถูกติด tools, system prompt และ context window แล้วผลัดเทิร์นกับผู้ใช้ = โมเดลที่ขยับได้

ทำไมต้องรู้
แยกให้ชัดจาก 'โมเดล' เวลาสั่งงาน จะได้รู้ว่าต้องแก้ชั้นไหน

System prompt

คำสั่งประจำตัว — คำสั่งที่ harness แปะไว้หน้าสุดของทุกรอบเรียก เป็นบรีฟถาวรของ agent

ทำไมต้องรู้
พฤติกรรมประหลาดที่เกิดทุกครั้ง มักมีรากอยู่ตรงนี้ ไม่ใช่ที่ข้อความล่าสุด

Session

เซสชัน — การใช้งานหนึ่งช่วงที่มีขอบเขต เริ่มจากว่าง สะสมไปเรื่อย จบเมื่อเคลียร์ ปิด หรือถูกบีบเข้าเซสชันใหม่

ทำไมต้องรู้
เป็นหน่วยที่ควรวางแผนงานให้พอดี — งานใหญ่เกินหนึ่ง session ต้องมีแผนส่งต่อ

Turn

เทิร์น — หนึ่งข้อความของผู้ใช้ บวกทุกอย่างที่ agent ทำตอบกลับ จนกว่าจะคืนคิวให้ผู้ใช้

ทำไมต้องรู้
หนึ่งเทิร์นอาจมีการเรียกโมเดลหลายรอบ — เวลาคิดเงินอย่านับเป็นหนึ่ง

Section 3

3 · เครื่องมือและสภาพแวดล้อม

agent รับรู้และเปลี่ยนแปลงโลกผ่าน tool อย่างเดียว ไม่มีทางอื่น

Environment

สภาพแวดล้อม — โลกที่ agent ลงมือทำ — ทุกอย่างนอก harness ที่มันเห็นผ่าน tool result และเปลี่ยนผ่าน tool call

ทำไมต้องรู้
จัดสภาพแวดล้อมให้ดี ได้ผลมากกว่าเขียน prompt ยาว ๆ

Filesystem

ระบบไฟล์ — ต้นไม้ของไฟล์และโฟลเดอร์ที่ agent อ่าน เขียน และรันคำสั่งอยู่ข้างใน

ทำไมต้องรู้
เป็นสภาพแวดล้อมมาตรฐานของ coding agent — โครงสร้างไฟล์ที่ดีคือ context ที่ดี

Tool

เครื่องมือ — ฟังก์ชันที่ harness เปิดให้ agent เรียก เช่น Read, Write, Bash, Search

ทำไมต้องรู้
ความสามารถของ agent ถูกจำกัดด้วยชุด tool ที่มี ไม่ใช่ด้วยความฉลาดอย่างเดียว

Tool call

การสั่งใช้เครื่องมือ — เอาต์พุตของโมเดลที่ระบุชื่อ tool กับอาร์กิวเมนต์ — เป็นแค่ข้อความมีโครงสร้าง

ทำไมต้องรู้
โมเดลไม่ได้ 'รัน' อะไรเอง harness ต่างหากที่อ่านแล้วรันให้

Tool result

ผลจากเครื่องมือ — สิ่งที่ harness ส่งกลับหลังรัน — เนื้อไฟล์ เอาต์พุต หรือ error

ทำไมต้องรู้
เป็นมุมมองเดียวที่ agent มีต่อสภาพแวดล้อม ถ้าผลลัพธ์ตัดทิ้ง agent ก็ตาบอดตรงนั้น

MCP

โปรโตคอลต่อเครื่องมือนอก — มาตรฐานสำหรับเสียบ tool server จากภายนอกเข้ากับ harness

ทำไมต้องรู้
ทางที่ agent จะได้ tool เกินกว่าที่ harness ให้มาตั้งแต่แรก

Permission request

การขออนุญาต — สิ่งที่ harness แสดงให้ผู้ใช้ดูก่อนรัน tool call ที่ยังไม่ได้อนุมัติล่วงหน้า

ทำไมต้องรู้
เป็นกลไกจริงที่ทำให้มนุษย์ยังอยู่ในลูป — ไม่ใช่แค่คำสัญญาใน prompt

Permission mode

โหมดสิทธิ์ — ส่วนที่กำหนดว่า tool call แบบไหนต้องถาม แบบไหนรันได้เลย

ทำไมต้องรู้
เปิดกว้างเกินไป = เสี่ยง แคบเกินไป = ถูกถามจนทำงานไม่ได้

Agent mode

โหมดการทำงาน — ชุดสำเร็จรูปที่รวมโหมดสิทธิ์เข้ากับคำสั่งพฤติกรรมที่ยัดเข้า system prompt สลับกลางทางได้

ทำไมต้องรู้
เปลี่ยนโหมดคือเปลี่ยนทั้งความเสี่ยงและนิสัยของ agent พร้อมกัน

Sandbox

กล่องทราย — สภาพแวดล้อมแยกที่ agent รันอยู่ข้างใน — container, VM หรือ shell จำกัดสิทธิ์

ทำไมต้องรู้
จำกัดรัศมีความเสียหายตอนสั่งงานแบบไม่นั่งเฝ้า

Section 4

4 · รูปแบบความพัง

รู้จักอาการก่อน จะได้ไม่เสียเวลาแก้ผิดจุด

Sycophancy

อาการเออออ — เอาต์พุตที่เห็นด้วยอย่างมั่นใจ เกิดจากการเทรนที่ให้รางวัลคำตอบที่มนุษย์ชอบ

ทำไมต้องรู้
ถามว่า 'แบบนี้ถูกไหม' แล้วได้ 'ถูกครับ' ไม่ใช่หลักฐาน ต้องให้มันหาหลักฐานค้าน

Hallucination

อาการหลอน — เอาต์พุตผิดแต่มั่นใจ มีสองแบบ: แต่งข้อเท็จจริงขึ้นมาเอง กับหลุดจาก context ที่โหลดไว้

ทำไมต้องรู้
สองแบบนี้แก้คนละทาง แบบแรกต้องโหลดเอกสาร แบบสองต้องลด context ให้สะอาด

Parametric knowledge

ความรู้ในตัวโมเดล — สิ่งที่โมเดลรู้จากการเทรน เก็บอยู่ในพารามิเตอร์ แช่แข็งไว้ตั้งแต่วันเทรน

ทำไมต้องรู้
อธิบายทั้งความเก่งฟรี ๆ และความมั่นใจผิด ๆ ในเรื่องที่เปลี่ยนไปแล้ว

Knowledge cutoff

วันตัดความรู้ — วันที่หลังจากนั้นโมเดลไม่มีความรู้ในตัวเลย

ทำไมต้องรู้
ไลบรารีหรือ API ที่ออกหลังวันนั้นคือกับดักการแต่งเรื่อง ถ้าไม่โหลดเอกสารจริงเข้าไป

Contextual knowledge

ความรู้จากบริบท — ข้อเท็จจริงที่ agent อ่านได้จาก context ตรงหน้าเดี๋ยวนี้ คู่ตรงข้ามของความรู้ในตัวโมเดล

ทำไมต้องรู้
เป็นช่องทางเดียวที่เราแก้ความรู้ผิดของโมเดลได้จริง

Attention relationship

ความสัมพันธ์ระหว่างโทเคน — การจับคู่ระหว่างโทเคนสองตัว คู่ที่เกี่ยวข้องกันจะส่งอิทธิพลต่อกันมากกว่า context ขนาด N โทเคนมีคู่แบบนี้ราว N²

ทำไมต้องรู้
รากของทุกปัญหาเรื่อง context ยาวแล้วโง่ลง

Attention budget

งบความสนใจ — โทเคนแต่ละตัวมีอิทธิพลจำกัดให้แจกจ่ายไปยังโทเคนอื่น และไม่ได้เพิ่มขึ้นเมื่อ context โตขึ้น

ทำไมต้องรู้
ยัดข้อมูลเพิ่มไม่ได้แปลว่าเข้าใจมากขึ้น มันแค่เจือจางลง

Attention degradation

ความสนใจเจือจาง — พอ session ยาวขึ้น งบความสนใจของแต่ละโทเคนถูกกระจายไปยังคู่แข่งมากขึ้น สัญญาณจึงอ่อนลง

ทำไมต้องรู้
อาการ 'คุยยาวแล้วลืมที่สั่งไว้ตอนต้น' มีที่มาเชิงกลไก ไม่ใช่นิสัย

Smart zone

ช่วงหัวสด — ช่วงต้น session ที่ agent คมและโฟกัส พอยาวขึ้นจะไหลเข้าช่วงมึน — สะเพร่า ลืม ผิดบ่อยขึ้น

ทำไมต้องรู้
งานสำคัญควรทำตอนหัวสด ไม่ใช่ท้าย session ที่ยาวมาแล้ว

Section 5

5 · การส่งต่องาน

งานใหญ่เกินหนึ่ง session เสมอ ตัวชี้วัดคือของที่ส่งต่อไปอ่านรู้เรื่องหรือเปล่า

Clearing

ล้างเริ่มใหม่ — จบ session ปัจจุบันแล้วเริ่มใหม่ ข้อความถัดไปเริ่มจาก context ว่างเปล่า

ทำไมต้องรู้
วิธีที่ถูกที่สุดในการกลับเข้าช่วงหัวสด แต่แลกด้วยการเสียบริบททั้งหมด

Handoff

การส่งต่อ — ย้าย context จาก session หนึ่งไปอีก session โดยไม่มีทางกลับ วิธีขนย้ายมีหลายแบบ

ทำไมต้องรู้
คุณภาพงานรอบถัดไปขึ้นกับคุณภาพการส่งต่อ ไม่ใช่ความเก่งของรอบถัดไป

Primary source

แหล่งปฐมภูมิ — ตัวของจริง — โค้ด transcript ข้อมูลดิบ ครบและเชื่อถือได้ แต่แพงเวลาโหลดเข้า context

ทำไมต้องรู้
ตอนต้องพิสูจน์ ต้องกลับมาที่นี่เสมอ

Secondary source

แหล่งทุติยภูมิ — คำบอกเล่าถึงของจริง ห่างออกมาหนึ่งชั้น — สรุป เอกสาร บทสรุปจากการบีบ context ถูกแต่ตกหล่นโดยธรรมชาติ

ทำไมต้องรู้
ประหยัดดี แต่ถ้าเถียงกันเรื่องข้อเท็จจริง อย่าใช้ตัวนี้ตัดสิน

Handoff artifact

เอกสารส่งต่อ — เอกสารที่ใช้เป็นตัวขนย้ายการส่งต่อ เขียนโดย session หนึ่งเพื่อให้อีก session อ่าน

ทำไมต้องรู้
ถ้าเขียนไว้แล้วรอบหน้าอ่านไม่รู้เรื่อง เท่ากับไม่ได้ส่งต่อ

Spec

สเปก — เอกสารส่งต่อที่อธิบายงานหลาย session — บอกว่ากำลังสร้างอะไร ไม่ใช่แต่ละรอบทำยังไง ประกอบขึ้นจากตั๋วงาน

ทำไมต้องรู้
เป็นตัวกันไม่ให้แต่ละ session ตีความเป้าหมายไปคนละทาง

Ticket

ตั๋วงาน — เอกสารส่งต่อที่กำหนดขอบเขตงานหนึ่ง session อยู่เดี่ยว ๆ หรือห้อยใต้สเปกก็ได้ และบล็อกกันเองได้

ทำไมต้องรู้
หน่วยงานที่พอดีกับหนึ่ง session คือหน่วยที่ agent ทำจบได้จริง

Compaction

การบีบบริบท — การส่งต่อที่ทำในหน่วยความจำ: สรุปประวัติของ session เดิมไปตั้งต้น session ใหม่ ตกหล่นเสมอ แลกรายละเอียดกับพื้นที่ว่าง

ทำไมต้องรู้
หลังบีบแล้วรายละเอียดหาย ต้องรู้ว่าอะไรหายก่อนจะเชื่อคำตอบต่อจากนั้น

Autocompact

บีบอัตโนมัติ — การบีบบริบทที่ harness สั่งเองเมื่อ context ใกล้เต็ม

ทำไมต้องรู้
มันเกิดโดยเราไม่ได้เลือกจังหวะ — งานสำคัญอย่าปล่อยให้ชนเพดานเอง

Section 6

6 · ความจำและการบังคับทิศ

วิธีทำให้ agent รู้สิ่งที่ควรรู้ โดยไม่ยัดทุกอย่างเข้า context

Memory system

ระบบความจำ — ระบบที่พยายามทำให้ agent จำข้ามเซสชันได้ ด้วยการเขียนลงสภาพแวดล้อมแล้วโหลดกลับตอนเริ่ม session

ทำไมต้องรู้
ไม่ใช่ความจำจริงของโมเดล เป็นการเขียน-อ่านไฟล์ ถ้า readback ไม่ผ่าน = ยังไม่ได้จำ

AGENTS.md

ไฟล์บรีฟประจำโปรเจกต์ — ไฟล์ในสภาพแวดล้อมที่ harness โหลดเข้า context ตอนเริ่ม session — บรีฟถาวรของโปรเจกต์ถึง agent

ทำไมต้องรู้
ที่ที่ควรเก็บกฎที่ต้องใช้ทุกครั้ง ไม่ใช่พิมพ์ซ้ำทุกเทิร์น

Progressive disclosure

เปิดเผยเป็นชั้น — โหลดเฉพาะ context ที่ต้องใช้ตอนนี้ ที่เหลือทิ้งตัวชี้ไว้ ยืมแนวคิดมาจากงานออกแบบ UI

ทำไมต้องรู้
ทางออกจริงของปัญหา context บวม — ไม่ใช่ซื้อ context window ใหญ่ขึ้น

Context pointer

ตัวชี้บริบท — การอ้างถึงเอกสารอื่นในเอกสารหนึ่ง เพื่อให้ agent ดึงเข้ามาเฉพาะตอนที่งานต้องใช้

ทำไมต้องรู้
ทำให้ไฟล์บรีฟสั้นได้โดยไม่เสียความครบ

Skill

สกิล — ความสามารถที่สอนได้ มัดรวมเป็นก้อน เก็บไว้นอก context จนกว่าตัวชี้บริบทจะดึงเข้ามาใช้

ทำไมต้องรู้
วิธีเพิ่มความสามารถโดยไม่กินที่ใน context ตลอดเวลา

Subagent

เอเจนต์ลูก — agent ที่ถูก agent อื่นสร้างผ่าน tool call รันใน session ของตัวเอง คืนผลกลับมาเป็น tool result ก้อนเดียว และแตกลูกต่อไม่ได้

ทำไมต้องรู้
ใช้กันงานค้นหาที่รกไม่ให้มาเปลือง context ของตัวหลัก

Section 7

7 · รูปแบบการทำงาน

เลือกโหมดการทำงานให้ตรงกับความเสี่ยงของงาน

Human-in-the-loop

มีคนอยู่ในลูป — รูปแบบที่มนุษย์ทำงานคู่กับ agent ระหว่าง session — คอยตรวจ เปลี่ยนทิศ หรือช่วยคิดแบบเรียลไทม์

ทำไมต้องรู้
โหมดที่เหมาะกับงานที่ผิดแล้วแก้ยาก

AFK

ปล่อยรันไม่นั่งเฝ้า — เริ่มงานแล้วเดินออกไป ปล่อย agent รันเอง

ทำไมต้องรู้
ความคลุมเครือที่เราไม่ได้เคลียร์ตอนต้น จะถูกมันเดาแล้วต่อยอดผิดไปทั้งกอง

Automated check

ตัวตรวจอัตโนมัติ — การตรวจแบบผลลัพธ์แน่นอนที่รันในสภาพแวดล้อม — test, type check, lint, build, pre-commit ผ่านหรือไม่ผ่าน ไม่มีการตีความ

ทำไมต้องรู้
เป็นตาแทนเราตอนไม่ได้เฝ้า และเถียงไม่ได้

Automated review

รีวิวโดย agent — ให้ agent ตัวหนึ่งรีวิวงานของอีกตัว มักใช้คนละโมเดลหรือคนละ system prompt ผลไม่คงที่เพราะเป็นการตีความ

ทำไมต้องรู้
จับปัญหาที่ test จับไม่ได้ แต่อย่าใช้แทนการตรวจของมนุษย์

Human review

รีวิวโดยมนุษย์ — ผู้ใช้อ่านโค้ดที่ agent เขียนแล้วตัดสินเอง — อ่าน diff ถึงนับ อ่านแต่บทสรุปไม่นับ

ทำไมต้องรู้
เส้นแบ่งจริงระหว่างงานที่ตรวจแล้วกับงานที่แค่ดูสวย

Vibe coding

โค้ดตามความรู้สึก — รับโค้ดที่ agent เขียนโดยไม่อ่าน มอง diff เป็นกล่องทึบ

ทำไมต้องรู้
เร็วมากสำหรับของทิ้งขว้าง และอันตรายมากสำหรับของที่ต้องดูแลต่อ

Design concept

ภาพร่วมของสิ่งที่จะสร้าง — ความเข้าใจร่วมกันว่ากำลังสร้างอะไร ถือร่วมกันระหว่างคนกับ agent แต่แยกจากตัวชิ้นงาน

ทำไมต้องรู้
ถ้าภาพนี้ไม่ตรงกัน โค้ดจะสวยแต่ผิดเรื่อง

Grilling

การซักไล่ — เทคนิคสร้างภาพร่วม โดยให้ agent สัมภาษณ์ผู้ใช้แบบซักทีละการตัดสินใจ

ทำไมต้องรู้
ดันความคลุมเครือขึ้นมาก่อนลงมือ ถูกกว่าค้นเจอทีหลังมาก

Prototyping

ทำตัวอย่างหยาบ — ให้ agent สร้างของหยาบ ๆ เร็ว ๆ เมื่อคุยกันอย่างเดียวแล้วยังเห็นไม่ตรงกัน

ทำไมต้องรู้
ของจริงชิ้นเล็กสื่อสารได้ชัดกว่าคำอธิบายยาว ๆ

DX

ประสบการณ์นักพัฒนา — โค้ดเบสและเครื่องมือทำให้มนุษย์ทำงานดีได้ง่ายแค่ไหน — เอกสาร ความเร็วของ feedback ข้อความ error

ทำไมต้องรู้
ของเดิมที่เราคุ้นอยู่แล้ว ใช้เป็นฐานเทียบกับ AX

AX

ประสบการณ์เอเจนต์ — สภาพแวดล้อมถูกจัดไว้ดีแค่ไหนให้ agent ทำงานได้ดี — ตัวตรวจ สถาปัตยกรรม และ context ที่เหลือให้ใช้

ทำไมต้องรู้
ตอนไม่มีใครเฝ้า สภาพแวดล้อมคือตัวช่วยเดียวที่ agent มี
